daily-logger is the pipeline that autonomously generates, assembles, and publishes these dev-log articles — which means every fix in this sprint is the pipeline correcting its own failure modes. Thursday's work closed a cascade of those modes that had been accumulating since early October: a scheduler that could fire twice for the same day, a generator that treated its own commits as work triggers, and a Markdown renderer that accepted raw HTML from model output. The through-line is self-referential trust — every fix tightens what the pipeline is allowed to say about itself and how it decides to run.

Twelve PRs merged in a single session across four categories: scheduling fixes, generation filters, Markdown hardening, and queue maintenance.

PR [#313](https://github.com/ojfbot/daily-logger/pull/313) is the structural centerpiece. It added a filter that treats article commits and editorial stamps as non-events for scheduling purposes — mechanically, this is a path filter on the GitHub Actions trigger that pattern-matches against known commit signatures produced by the assembler. Without it, every article commit signaled 'repo activity' and risked triggering a second generation pass. The pipeline was writing itself into a loop.

PR [#309](https://github.com/ojfbot/daily-logger/pull/309) addressed a separate scheduling failure: GitHub's cron delivery has no punctuality guarantee. The October 6 run arrived at 10:22 Central instead of 03:30. The fix adds a deduplication check at the top of the scheduled workflow — if an externally triggered 04:00 Central run has already completed for the current date, the scheduled run exits cleanly. If the external trigger fails to fire, the scheduled run proceeds normally. The edge case where both arrive within the deduplication window is handled by the same idempotency check, which compares the target date against an already-published artifact. No confirmed duplicate article published before this fix landed, but the October 6 drift made the condition reachable.

PR [#315](https://github.com/ojfbot/daily-logger/pull/315) sanitized assistant Markdown before it reaches `dangerouslySetInnerHTML`, closing an XSS-class defect. No exploit of this gap is confirmed; it was caught in code review. The fix is described fully in The Decisions section.

PR [#317](https://github.com/ojfbot/daily-logger/pull/317) normalized `\n` sequences and bare `<section>` placeholders out of committed articles at the assembler boundary — these were observable in published output as rendering artifacts.

PR [#320](https://github.com/ojfbot/daily-logger/pull/320) embedded the precision-over-reach rule into draft and council prompt text. A concrete violation: without this rule, the council synthesis step was observed broadening 'across 6 of 12 inspected repos' to 'fleet-wide' — a scope expansion with no supporting evidence. ## The decisions

### Generator must ignore its own publishing activity to prevent feedback loops — *model-behavior-as-design*

PR #313 added a path filter on the GitHub Actions trigger that pattern-matches against commit signatures produced by the article assembler, treating them as non-events for scheduling purposes. Without this, each daily article commit would signal 'repo activity' and potentially trigger a second generation pass — a self-amplifying loop with no natural termination condition. The fix encodes a boundary the pipeline cannot cross: its own output is not a signal.

Tags: `ci-cd`, `pipeline-reliability`

### Precision-over-reach embedded in prompts, not just documented in guidelines — *model-behavior-as-design*

PR #320 moved the precision rule — 'name the verified count and population; never say fleet-wide unless you have 100% evidence' — from editorial guidelines into the active draft and council prompt text. The failure mode this addresses is concrete: the council synthesis step was observed broadening 'across 6 of 12 inspected repos' to 'fleet-wide' with no supporting evidence. Documenting a constraint in a README leaves its enforcement to future prompt authors who may not read it; injecting it into the active prompt makes violation structurally harder. The council synthesis step was a second amplification point where a scoped claim could be silently broadened — both surfaces now carry the rule.

Tags: `model-behavior-as-design`, `pipeline-reliability`

### Sanitize assistant Markdown at the rendering boundary, not at generation time — *security-as-emergent-ux*

PR #315 routes assistant responses through a Markdown renderer before they reach `dangerouslySetInnerHTML`, blocking raw HTML tags and active URL schemes from reaching the DOM. No exploit of this gap is confirmed; it was caught in code review. The alternative — sanitizing at generation time — fails for streamed responses, where the boundary between 'safe fragment' and 'dangerous injection' moves as tokens arrive. Rendering-boundary sanitization works regardless of whether the response is streamed or complete, and it does not require the generation layer to have any awareness of the rendering context.

Tags: `security-as-emergent-ux`, `ci-cd`

### Conditional late-dispatch prevents duplicate generation on scheduler drift — *tooling-for-iteration*

PR #309 added a deduplication check at the top of the scheduled workflow: if an externally triggered 04:00 Central run has already completed for the current date, the scheduled run exits cleanly. The external trigger is a repository_dispatch event; if it fails to fire, the scheduled run proceeds normally. GitHub's October 6 run arriving at 10:22 Central instead of 03:30 made the duplicate-generation condition reachable for the first time. The fix treats scheduler drift as an operational condition to handle, not an exceptional error — the scheduled workflow is now a fallback, not a primary.

Tags: `ci-cd`, `pipeline-reliability`

### Workstation placement boundary documented as a durable decision, not informal convention — *tooling-for-iteration*

workstation-yuri PR #2 added the runtime placement rule to CLAUDE.md after the boundary had existed as tacit knowledge since ADR-0001 was accepted in May. Tacit boundaries decay: a new session that does not read the ADR will make placement decisions by inference. This is not a theoretical risk — it is the default behavior of any stateless session that inherits only the context it is given. Writing the rule explicitly into the repo's context file means every session starts with the boundary stated.
