Friday's work was two parallel hardening efforts converging on the same property: trust in what lands on main. In daily-logger, commits tightened the editorial CI boundary — ensuring that generated and editorial PR heads actually run required checks rather than bypassing them with `[skip ci]`. ## What shipped

### daily-logger ([#329](https://github.com/ojfbot/daily-logger/pull/329), [#328](https://github.com/ojfbot/daily-logger/pull/328), [#327](https://github.com/ojfbot/daily-logger/pull/327), [#326](https://github.com/ojfbot/daily-logger/pull/326))

Five fixes and one documentation commit tightened the editorial CI boundary across PRs [#326](https://github.com/ojfbot/daily-logger/pull/326)–[#329](https://github.com/ojfbot/daily-logger/pull/329). The root problem: generated article commits carried `[skip ci]` to prevent recursive pipeline triggers, but that same tag was suppressing the required status checks that protect the editorial merge gate. Additionally, editorial stamp pushes used the default `GITHUB_TOKEN`, making the push actor indistinguishable from any other workflow step — meaning a compromised downstream step could impersonate the editorial actor.

PR [#329](https://github.com/ojfbot/daily-logger/pull/329) merged, resolving the skip-ci conflict: GitHub's branch protection ruleset evaluates required status checks independently of the `[skip ci]` tag on individual commits, but only when the ruleset explicitly names those checks as required on the PR head ref. The fix adds that explicit requirement to the branch protection rule, so the gate fires on the PR head regardless of what any individual commit carries. Generation commits may still use `[skip ci]` for anti-recursion; the gate check is no longer suppressible by that signal.

A separate fix isolated editorial push credentials behind an article-only validation boundary, scoped so that a compromised downstream step cannot impersonate the editorial actor. The specific credential is a GitHub App installation token with permissions narrowed to the article validation context — it is not the default `GITHUB_TOKEN` and not a broad PAT. A `.gitignore` update excluded local Python test bytecode.

### core ([#509](https://github.com/ojfbot/core/pull/509))

Two commits delivered and merged PR [#509](https://github.com/ojfbot/core/pull/509): a live ruleset inspection found 16 of 24 active public ojfbot repositories lacked a no-bypass PR gate on the default branch. The 8 remaining repositories are unconfirmed — not confirmed compliant and not confirmed unprotected. They were not excluded because they have stricter rules; they were not reached conclusively by the inspection pass. They are actively unprotected until the next audit run confirms otherwise, and should be treated as such.

The feat commit (`163f77a`) applies ruleset enforcement across the 16 affected repositories in a single commit, making the coverage change auditable from one diff. The fix commit (`8d90aad`) handles the safety case: when the fleet-runner encounters a repository that already has a ruleset, it now refuses and preserves — if the existing rule is stricter on any dimension, the repair is rejected rather than applied. When the ambiguity check fires, the fleet-runner exits nonzero and writes the conflict to its run log; it does not file an issue automatically, so the operator must check the run output. Rollback path: the single-commit application means a `git revert` on `163f77a` removes all 16 gate additions simultaneously — the same auditability that makes the commit clean also makes the revert clean, though it should be followed by a manual inspection pass to confirm no repo-specific state was lost.

'No-bypass' in GitHub Ruleset terms means the rule applies to all actors including repository admins and GitHub App tokens — there is no quiet admin carve-out. The workflow actor that ran the fleet-runner is subject to the same gate on subsequent pushes.

## The decisions

### Require CI on editorial PR heads even when commits carry [skip ci] — *security-as-emergent-ux*

The `[skip ci]` tag was the right guard for preventing recursive pipeline triggers, but it was also suppressing the required status checks that protect the editorial merge path. GitHub's branch protection ruleset can evaluate required status checks against the PR head ref independently of commit-level skip signals — but only when the ruleset explicitly names those checks as required on the head. PR #329 adds that explicit requirement. Generation commits may still carry `[skip ci]` to avoid recursive triggering; the branch protection gate now fires on the PR head regardless, overriding the skip signal for the gate check. Anyone debugging a failed editorial merge should look at the required status check named in the branch protection ruleset for `daily-logger`, not at the individual commit flags.

### Isolate editorial push credentials behind an article-only validation boundary — *security-as-emergent-ux*

Editorial stamp pushes previously used the default `GITHUB_TOKEN`, which meant the push actor was indistinguishable from any other workflow step. The fix replaces that with a GitHub App installation token scoped narrowly to the article validation context — it cannot be used by downstream workflow steps for anything outside that boundary. The isolation guarantee: a compromised downstream step cannot impersonate the editorial actor, because the credential is not available to it. This is the same principle as the no-bypass PR gate — trust granted at the narrowest scope that satisfies the use case. 'Security-as-emergent-ux' here means the pipeline's trustworthiness is a property a developer experiences every time a generated article lands cleanly on main without manual intervention; the credential boundary is what makes that experience reliable rather than fragile.

Tags: `ci-cd`, `hardening`, `daily-logger`

### Refuse ambiguous policy repairs that could weaken existing rules — *security-as-emergent-ux*

When the fleet-runner applies a PR-gate ruleset to a repository that already has a ruleset, there's an ambiguity: should the new rule replace the existing one, merge with it, or be rejected? Commit `8d90aad` encodes 'refuse and preserve' as the default: if the existing rule is stricter on any dimension, the repair is rejected rather than applied. The fleet-runner exits nonzero and writes the conflict to its run log; the operator must check run output to detect a refused repair. This is a deliberate asymmetry — weakening a gate is always worse than leaving a gap, because a weakened gate silently removes protection that an operator may be depending on. The alternative, 'merge and apply,' would require the fleet-runner to understand every dimension of every existing ruleset and get that union correct every time. The failure mode of 'refuse and preserve' is a missed hardening opportunity; the failure mode of 'merge and apply' is silent regression. The safer failure mode was chosen.

### Fleet-wide PR gate enforcement as a single auditable commit — *security-as-emergent-ux*

Rather than patching repositories one at a time, `163f77a` applied no-bypass PR gates across 16 repositories in a single core commit. The benefit: coverage change is auditable from one diff, and the revert path is equally clean — `git revert 163f77a` removes all 16 additions simultaneously. The risk: a defect in the fleet-runner logic that the ambiguity-rejection check didn't catch would affect all 16 at once. That risk was accepted because `8d90aad` landed in the same session and because the alternative — 16 separate commits — would leave intermediate states undocumented and make coverage verification impossible from a single diff. The no-bypass rule applies to all actors including repository admins and GitHub App tokens; there is no admin carve-out.
