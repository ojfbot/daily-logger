## The decisions

### Classic Space Venue dev-host uses labeled mock data behind a provenance header while live fleet-runner read projection is pending — *model-behavior-as-design*

Rather than blocking visible UI work on a live fleet-runner read-projection endpoint, the dev-host serves a hand-written fixture shaped like the v0 read-projection contract. A read-projection row represents the state of a fleet-runner work item as the venue needs to display it — fields are not yet publicly attested beyond what the mock fixture exposes. Provenance is set at every row level (provenance: simulated), surfaced via an X-Data-Provenance: simulated HTTP header, and held persistent as an amber SIMULATED DATA label at 7.5:1 contrast. This makes the scope of simulation explicit at every layer — HTTP, JSON, and visual — so operator screenshots cannot be misread as live data. Core #561 (fleet-runner read-projection v0) is the named architectural prerequisite before any real data flows in; its owner and delivery timeline are not attested in current evidence, which means the dev-host is on mocked data indefinitely until that issue resolves.

### Root AGENTS.md names core map and fleet boundaries; bundle scene guidance lives in walkway-pass/AGENTS.md — *assistant-centric*

PR #3 relocated scene-specific agent instructions from root AGENTS.md to walkway-pass/AGENTS.md so that the file an agent reads on repo entry states governance constraints (core wayfinder map, fleet boundaries) rather than scene mechanics. The prior state put ChatGPT bundle scene notes at root, which Codex would read as standing instructions. This is not theoretical: the fleet has previously observed Codex treating scene-specific root instructions as governance-level standing instructions, producing incorrect scope assumptions in generated code. Scoping the root file to governance and the scene file to mechanics prevents that substitution by keeping the context an agent receives on entry proportional to the decisions it is authorized to make.

### Design bible intake preserves the immutable supplied kit and isolates derivative repairs in a separate consumer harness — *tooling-for-iteration*

The v0.5 design bible kit is stored unmodified at design-bible/v0.5/ with its 199 original manifest hashes passing intact; the R13a keyboard-focus repair lives in a separate design-bible/consumer-harness/ tree. The kit is treated as immutable not because the source is uncontrollable in principle, but because mixing repair code into the supplied kit would make it impossible to compare against future Claude Design deliveries or audit which changes are ours versus the original. The R13a repair corrects a keyboard-focus accessibility regression in the kit's output; a corrected kit re-delivery was not the chosen path because the repair is a known, bounded change that the consumer harness can own without requiring a new kit version. The design bible itself is consumed by Codex agents working on the venue — the consumer harness is the integration point, not a human design review workflow.

### Acceptance pipeline now requires the complete saved evidence binding before deriving Accepted status — *security-as-emergent-ux*

PR #414 identified that the web interface could stage Accepted status while the saved evidence map was still tied to Draft. Mechanically: acceptance derives a binding — a content-addressed map from each suggestion to its evidence record — and the bug allowed that derivation to proceed from a stale Draft-era binding rather than reconstructing it from the current Draft view. The fix reconstructs the prior Draft view and requires a complete saved binding match before the Accepted-status binding is derived, preserving the transition's lineage. The correctness guarantee now in place: an Accepted article's evidence binding must have been derived from a view that exactly matches the saved Draft state — if that match cannot be established, the acceptance is rejected. Without this, acceptance could silently advance against evidence that was never verified against the current article content.

### Action reviews now bind to explicit per-suggestion evidence requirements rather than treating historical citations as current requirements — *model-behavior-as-design*

PR #413 found that action review could treat a historical citation as a current work requirement, and that revision or acceptance could then collect evidence from a stale case — the same suggestion in a later review cycle would carry evidence requirements from an earlier run. The fix records explicit evidence requirements for each original suggestion at the time of generation and prepares the same inputs before evidence collection in generation, revision, and acceptance. Identical retries reuse a verified result; changed cases require current input bindings. This closes the gap where a suggestion's evidence lineage could silently drift across review cycles.

Tags: `editorial-pipeline`, `model-behavior-as-design`

### Oversized evidence leaves a typed, auditable pending request rather than silently failing — *tooling-for-iteration*

PR #411 changed the evidence-recovery path: when a source exceeds the per-source size limit or is missing, the system now emits a typed pending request rather than blocking silently. A pending request is a structured record — not a file, env var, or implicit state — that names the source, the failure reason, and what local artifact would satisfy it. The operator answers the pending request locally using private local artifacts (content that cannot be committed to the public repo), and the pipeline resumes from that answered state. Post-commit retries recover the exact committed result without repeating admission prompts or losing the result to a missing local receipt. This is the operative path for daily-logger #417, which is working through evidence-size coverage for October 21.
