A security gap is a UX gap: Chrome's Local Network Access permission prompt was the first thing every visitor to frame.jim.software saw, because cv-builder's Settings remote was reaching for http://localhost in production bundles. Wednesday closed that for cv-builder and confirmed the same pattern in two more sub-apps — making the fleet-wide shape of the problem visible before it could be dismissed as a one-off.

## What shipped

### cv-builder

PR [#157](https://github.com/ojfbot/cv-builder/pull/157) merged at 13:29Z. The browser-app bundle was shipping with a hardcoded `http://localhost` API origin because the environment guard was absent — or applied only during development builds. In Vite, `import.meta.env.*` values are compile-time string replacements, not runtime values. When `VITE_API_URL` is unset at build time, Vite replaces the expression with an empty string or leaves the fallback literal — whichever the code specifies. The fix removes the localhost fallback and asserts the production URL at build time, so an unset `VITE_API_URL` fails the build rather than silently defaulting to localhost. The Module Federation context makes this failure mode worse than a normal SPA: when the shell mounts a remote at a host origin (frame.jim.software), and that remote's bootstrapped code fires a fetch to http://localhost, Chrome classifies the request as a Local Network Access attempt from a public origin — triggering a permission prompt. In a normal SPA, the same bad URL would produce a silent network error. The remote execution context is what escalates a misconfiguration into a visible UX failure. Frame.jim.software is still not fully clean after this merge: gastown-pilot ([#19](https://github.com/ojfbot/cv-builder/pull/19)) and BlogEngine ([#59](https://github.com/ojfbot/cv-builder/pull/59)) carry the same pattern and those PRs have not merged. Any external viewer right now will still see prompts from those two remotes.

## The decisions

### Gate API base URLs on a build-time assertion, not a compile-time constant with a localhost fallback — *security-as-emergent-ux*

The fix in #157 removes the localhost fallback from the VITE_API_URL expression so that an unset variable fails the build rather than silently producing a localhost URL in production bundles. This is technically a build-time assertion, not a true runtime resolution — 'runtime signal' in the draft was imprecise. A genuine runtime resolution would read from something like window.__FRAME_CONFIG__ injected by the server; that's a stronger approach but not what shipped. What shipped is correct and safe: production bundles now have no path to a localhost origin. The environment variable contract — name, required/optional status, production-safe fallback — needs an ADR before a fourth sub-app ships the same bug. core #495 is open but covers speech-act tiers, not environment resolution. That gap is unaddressed.

### Treat the localhost-in-production bug as a fleet-wide pattern; audit before the next sub-app ships — *tooling-for-iteration*

The same localhost-reach pattern in gastown-pilot (#19) and BlogEngine (#59) — both opened the same day as #157 — confirms this is a shared architectural gap baked into the sub-app template, not a cv-builder quirk. Every Frame sub-app built with a Vite dev-server default and deployed behind Module Federation can exhibit this until the template changes. The right fix is a shared resolveApiBase() utility — or equivalent build-time assertion — in the sub-app scaffolding, so the fourth sub-app does not require a fourth PR. The utility contract needs to define: which environment variable(s) it reads, what happens when none are set (fail build, fall back to host origin, or throw at runtime), and how it stays in sync across independently-bundled remotes. Those questions are unanswered. Three sub-apps are affected today: cv-builder (fixed), gastown-pilot (open, more severe), BlogEngine (open). No other sub-apps are confirmed clean — the audit did not extend beyond the three where the pattern was already visible. A one-line schematic of the before/after: `const API_BASE = import.meta.env.VITE_API_URL ?? 'http://localhost:PORT'` → `const API_BASE = import.meta.env.VITE_API_URL` with a build assertion that rejects empty strings. Anyone applying the gastown-pilot or BlogEngine fix should look for that ?? fallback pattern in the browser-app entry point.

**2. Write the ADR for environment resolution before the fourth sub-app ships.**
Three repos hit this bug in parallel because there was no written contract for how Frame sub-apps resolve their API base URL in production. The ADR needs to specify: the environment variable name(s), whether the variable is required or optional, what the production-safe fallback is (the correct answer is probably "fail the build"), and who owns the shared utility once it exists. core #495 is open but covers a different topic. This ADR is a gap.

**3. Extract `resolveApiBase()` after #19 and #59 merge, not before.**
Three near-identical PRs is the canonical signal for a shared abstraction. But the utility belongs after the immediate fixes, not instead of them — #19 and #59 are on fire and need to close first. Once they merge, the right move is to scaffold `resolveApiBase()` in frame-ui-components (or a shared config package), define the contract in the ADR, update the sub-app template so the fifth sub-app can't repeat this, and optionally backport to the three repos that already have the inline fix. The target is the sub-app template, not the three repos that already have patches. The timing is: after #19 and #59 merge, before the next sub-app wires up an API.
