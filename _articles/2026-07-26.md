## The decisions

### QuestionNode carries a substrate_call binding, never a result — *model-behavior-as-design*

A QuestionNode is a JSON record in registry/ with fields including id, natural_language_query, substrate_call (a structured object specifying the f1-substrate endpoint name and argument schema), and metadata. The substrate_call field stores which call to invoke and how — not the computed answer. This means doctrine nodes never go stale on data refresh: a new race season changes the numbers in f1-substrate, but the question framing in f1-doctrine remains valid. If the binding were a result field instead, every data refresh would silently invalidate 33 nodes and the assistant would surface confident-but-wrong suggestions. The separation also preserves the architecture's core invariant: f1-doctrine asks, f1-substrate computes. At runtime, when the assistant resolves a QuestionNode, it reads the substrate_call binding, dispatches the call to f1-substrate, and surfaces the result — f1-doctrine never touches the data itself.

### ADR-0003: Seven-value race_progress replaces three-value phase, but stint_position is under test — *model-behavior-as-design*

S1 decomposed the coarse phase axis (pre_race | in_race | post_race) into seven granular race_progress values to give the relevance gate finer signal. However, the phase-keying gate — a structured prompt evaluation run against a sealed gold set of 47 human-labelled question/context pairs, scored by NDCG — recorded that stint_position contributed +0.000 uplift compared to the A3 (without stint_position) arm. On a 47-example gold set, +0.000 is not noise suppression; it is a genuine null result. The axis may collapse in S4 if blind-judge scoring confirms it. Formalising this as ADR-0003 forces the decision to be revisited with data rather than intuition — the axis stays in for now but is explicitly on probation. ADR-0001 (RAQG boundary: doctrine asks, substrate computes, never the reverse) and ADR-0002 (tiered authority: f1-substrate owns ground truth, f1-doctrine owns question framing, f1-pit-wall owns corpus provenance) are also formally accepted; both are recorded at registry/adr/.

### Migration surfaced upstream data defects rather than papering over them — *tooling-for-iteration*

When f1-doctrine S1 migrated the 33 nl-query-corpus entries, it found two confirmed data defects in the source — both entries carry malformed substrate_call references that do not resolve to a live f1-substrate endpoint — and filed them as a handoff brief (f1-pit-wall PR #6) rather than silently absorbing them into the registry. This keeps the registry's provenance trustworthy: a defect that enters the committed question layer would propagate into every downstream evaluation and retriever test. The cost is explicit and accepted: S2 is gated on f1-pit-wall fixing the defect entries before the registry can be used as a training baseline. The defect characterisation in PR #6 names the exact entries and correct values; the fix is a targeted JSON edit, not an investigation.
