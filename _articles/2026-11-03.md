## The decisions

### Event-sourced ledger as the single source of truth (L-1 / L-2) — *assistant-centric*

Every pipeline action — image ingestion, OCR reading, catalog lookup, adjudication — is appended as an immutable event to a SQLite ledger (node:sqlite with WAL mode). View tables are updated incrementally in the same append transaction; a refused event leaves nothing. replay() must produce byte-identical view state, and the suite verifies this property. No event can be updated or deleted (enforced by trigger), and seq is kept gap-free.

SQLite with WAL was chosen over a flat append-only log because it provides atomic multi-table transactions and queryable views without a server process — appropriate for a single-workstation pipeline owned by one person. The trade-off acknowledged: if this pipeline ever runs across multiple machines, the storage layer would need revisiting. That decision is deferred and not yet an ADR.

What happens when replay diverges: the test suite runs replay() and compares output against a known fixture snapshot; a byte mismatch fails the suite before any merge. Schema migrations between events are a known future risk with no mitigation yet filed — acknowledged as an open gap.

### Privacy guard as a machine-enforced boundary, not a policy statement (Z-1) — *security-as-emergent-ux*

The OC9 public/private boundary — no photos, crops, OCR text, private paths, or model weights in the repo — is enforced by a pre-commit hook, a CI workflow on every PR and push, and a pnpm guard --history full-history scanner. OC9 is the fleet's constraint class for owner-content privacy: it defines what is never committed regardless of context.

The rule is not a comment in a README; it is a script that will fail a commit. A new contributor cannot accidentally push private data even if they have never read the policy, and CI catches it before review. This is the distinction between policy-as-documentation and policy-as-enforcement — and it matters most for the first contributor who hasn't read anything.

### Open-weight models label everything; no hand-labelling queue (OC36) — *model-behavior-as-design*

After a Label Studio trial (V-1a), the owner ruled out human annotation entirely. The trial surfaced that annotation workflow friction — setup, queue management, adjudication UI — would require recurring owner time per batch, which contradicts the design goal of a pipeline that runs unattended. The ruling: if two open-weight readers (SAM 3 for boxes, Florence-2 and Qwen2.5-VL for reading) cannot independently name the same ISFDB work, the spine stays unknown with a reason recorded. No human fallback queue exists.

This trades recall on ambiguous spines for a pipeline that requires zero owner time per photo run. 'Zero owner time per photo' is accurate for the labelling step specifically. Owner time is present elsewhere in the system — O-4 captured owner profile review answers, and the public seeds file requires explicit approval — but it is concentrated at curation milestones rather than distributed across every annotation.

The actual false-negative rate on pilot-000 (what fraction of spines resolved to unknown) is the open question that C-4 (BookcaseDiscovery #27) exists to answer. That number is not yet in the record.

### ISFDB as the canonical catalog backend, indexed locally via streaming mysqldump parser — *tooling-for-iteration*

C-1 stages the ISFDB dump (368 MB zipped, 1.6 GB as a dump) into a local SQLite database using a TypeScript byte-level state machine — no MySQL server required. FTS5 trigram indexes over title, author, and series forms support fuzzy fragment queries like GIBS NEUROM. The result is 340,829 root works and 943,917 editions available offline, with no API rate limits and no terms-of-service constraints on local indexing.

The parser is pinned to the current ISFDB dump schema. A format change in a future ISFDB export would require a manual parser update — this is an acknowledged maintenance risk with no automated protection yet filed.

### Reading profile as a typed model with public seeds and configurable weights (R-0 / R-1) — *assistant-centric*

Taste is represented as a typed TypeScript model (src/recommend/profile.ts) with entries (subject, relation, provenance), taste nodes, and configurable seed weights (w_read_all 0.6, liked 1.0, read-one 0.3). The public seeds file (profile/seeds.json) contains only facts the owner has explicitly approved for public commit — no private reading history enters the repo. Owner review answers (O-4) are recorded as named seed entries with provenance, making the taste model's decisions traceable.

The profile exists and is populated. R-2 (recommendation generation) has not started. Until R-2 merges, the taste model has no consumer: it is infrastructure awaiting its output layer. C-4's catalog coverage measurement is the stated prerequisite before R-2 work begins — C-4 blocks R-2.
