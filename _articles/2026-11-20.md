## The decisions

### Practice stops must be inspectable before a live proof attempt is authorized — *security-as-emergent-ux*

PR #630 adds an opt-in practice mode that exercises the full worker-stop and takeover path in isolation, requiring both clean worker receipts and a final empty queue snapshot before cleanup is considered complete. "Inspectable" here is a concrete capability: the worker receipt and queue snapshot are structured artifacts written to known locations during the practice run, available for post-hoc review without re-running the proof. Without this, the only evidence that G4 would work correctly was a source-read — the first time a stop silently failed mid-proof, there would be no structured artifact to diagnose against. The G4 milestone required that this failure mode be closeable from evidence, not inference; that requirement is now met.

"Security-as-emergent-ux" is a named project pillar: security properties are designed to surface as observable, user-visible behaviors — inspectable artifacts, explicit receipts, structured diagnostics — rather than as hidden invariants that only fail loudly in production. The practice stop inspection is a direct application: the safety property (clean handoff confirmed) is made visible as a reviewable artifact before any live window is consumed.

### Installer must reject unsafe version folder names before any filesystem effect — *security-as-emergent-ux*

PR #632 validates prerelease SemVer strings and rejects malformed or overlong folder names at the versioned worker installer's entry point, before any disk write occurs. The concrete failure mode the alternative creates: a partial install that passes the directory-exists check but contains an incomplete artifact set. The installer's own integrity checks compare against a manifest of expected files — a partial write can satisfy the manifest if the write was interrupted after the manifest was laid down, meaning a corrupted install silently passes as clean. The next deploy then diffs against a corrupted baseline rather than a known-good one. Rejecting at the entry point eliminates the partial-write class entirely for the validated input set.

### Proof startup codes are diagnostic contracts, not arbitrary strings, and must not be redacted — *tooling-for-iteration*

PR #633 separates fixed internal proof invariant codes — which carry semantic meaning to downstream diagnostic consumers — from arbitrary messages and path-like content that must be redacted for privacy. The "downstream diagnostic consumers" are the CI pipeline and any operator reading the structured startup log: the invariant codes are a small enumerated set (not free-form strings) that signal which phase of the startup sequence completed or failed. A regex-based redaction pass was treating them as path-like content because they matched a broad pattern. Blanket redaction of all startup-phase output had masked a legitimate CI failure mode where the startup code itself was the signal — the failure appeared as a missing code rather than an error message, which the redaction-unaware consumer interpreted as a phase that never ran.
