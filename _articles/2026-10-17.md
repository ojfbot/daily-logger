## The decisions

### Reviewer identity is the claimed name in review data, not the authenticated GitHub sender — *model-behavior-as-design*

The UI now explicitly distinguishes who the review record says reviewed the article — the claimed reviewer/model identity embedded in the JSON payload — from who the authenticated GitHub OAuth sender is. In the data model, these are separate fields: `reviewer` carries the claimed identity (a model name or editor handle from the review JSON) and `sender` carries the GitHub-authenticated account. Collapsing the two caused confusion when Codex sessions and human editors touched the same review record: GitHub sender attribution was overwriting model attribution. Separating them makes multi-reviewer and human-plus-model cycles legible, and gives future identity types (a third reviewer, an audit agent) a clear place to live without touching either existing field.

Tags: `editorial-pipeline`, `provenance`, `model-behavior-as-design`

### Feedback selection survives interruption via deliberate clear-or-preserve semantics — *model-behavior-as-design*

Rather than always preserving selected feedback across interrupted requests (which can surface stale selections in a new review context) or always discarding it (which loses editor work on transient failures), the UI now makes a deliberate binary choice at the point the request fires: a context flag is set before the request is dispatched, recording whether this is a same-context retry or a context-change navigation. On a timed-out or network-failed request the flag signals preserve; on a version bump or article switch the flag signals clear. This is a model-behavior-as-design decision — the system's behavior during failure is itself the UX, not a secondary concern — and it is the clearest expression of that principle shipped this week. The detection is pre-flight, not response-code inference, which is why a timeout during a version bump cannot be misread as a transient retry.

Tags: `model-behavior-as-design`, `hardening`, `editorial-pipeline`

### Proposed reviews are discoverable before they merge via PR head validation — *assistant-centric*

Before #368, the article UI could only surface reviews already merged into main — meaning the review needed to request corrections was invisible until after it was accepted. The fix validates four things server-side before returning findings: (1) the PR's immutable head SHA, confirming the tip hasn't moved; (2) the changed-file boundary, confirming the PR touches only expected review-data paths; (3) the registry manifest, confirming the review record is well-formed and registered; (4) the source article blob, confirming it matches the article the review claims to cover. Each check has a distinct failure mode: head mismatch and changed-file boundary violations return explicit rejection errors; manifest and blob failures disable writes with a visible explanation rather than silently passing. Stale or incomplete history also disables writes explicitly. This turns the review surface into a pre-merge tool rather than a post-merge history reader.

Tags: `assistant-centric`, `provenance`, `ci-cd`

### Section discussion is durable via GitHub as the correspondence store — *security-as-emergent-ux*

Discussion threaded against article sections was previously ephemeral browser state — it vanished on reload. #368 replaced that with GitHub as the backing store. A save-note operation records the exact text, account attribution, and correspondence target (the PR number plus section ID pair) without a provider call or article acceptance. Reload restores all three. GitHub was chosen over a separate database or localStorage because it keeps correspondence auditable, co-located with the PR review record, and requires no new infrastructure. The failure modes of this choice are not yet formally characterized: GitHub's API has availability SLAs that are not 99.99%, and rate-limiting could affect high-volume review cycles. Graceful degradation behavior under GitHub API unavailability is not documented in this PR and is not yet covered by an ADR.

Tags: `provenance`, `assistant-centric`, `editorial-pipeline`

### Action queue identity is strictly preserved across reconciliation — no re-paraphrasing — *tooling-for-iteration*

#373's reconciliation treated original action descriptions, IDs, and completion objects as immutable. Three missing October 15 suggestions were restored and three October 16 records were resolved without touching any other row's identity. The queue feeds both the Actions page and future drafting context — any identity drift causes downstream matching to fail silently, causing actions to re-open as false duplicates. The 85-open / 125-complete count is the verified post-reconciliation state. Whether 85 open actions is a healthy working backlog or a growing graveyard requires week-over-week queue-growth data not available in this report.
