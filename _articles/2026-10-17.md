## The decisions

### Reviewer identity is the claimed name in review data, not the authenticated GitHub carrier — *model-behavior-as-design*

The UI now explicitly distinguishes who the review record says reviewed the article — the claimed `reviewer.name` and `reviewer.sessionId` embedded in the review JSON — from the authenticated GitHub carrier (`pullRequest.author` when the review is linked through a PR). In the data model, these are separate paths: `reviewer.name`/`reviewer.sessionId` carry the claimed identity (a model name or editor handle from the review JSON) and `pullRequest.author` carries the GitHub-authenticated account when present. Presentation ambiguity arose when Codex sessions and human editors touched the same review record: the component now explicitly labels reviewer/session claims separately from the authenticated GitHub carrier. Separating them makes multi-reviewer and human-plus-model cycles legible, and gives future identity types (a third reviewer, an audit agent) a clear place to live without touching either existing path. When no PR link is available, the component explicitly displays “GitHub submission account not linked to this record.” It does not infer a submitting account from the reviewer claim.

### Feedback selection survives interruption via keyed storage, selective pruning, and deliberate clear — *model-behavior-as-design*

Rather than always preserving selected feedback across interrupted requests or always discarding it, the component keys saved drafts by actor, date, and article blob. On reload or reconnection, selections whose source findings are unavailable are retained (the absence of evidence is not treated as evidence that a finding is ineligible); selections whose source findings are present but no longer current or open are pruned. While a request is in flight, pruning is skipped — the component does not discard selections during an uncertain send. The editor can deliberately clear retained selections when a request is not being sent and selections exist; the control is disabled during a send or when there is nothing to clear. Editable feedback is preserved. This is a model-behavior-as-design decision — the system's behavior during failure is itself the UX, not a secondary concern. The tested paths cover reload-after-save, in-flight retention, and deliberate clear; broader timeout/navigation guarantees beyond those tested paths are not claimed.

### Automatic discovery of eligible review PRs complements explicit proposal registration — *assistant-centric*

Before #368, the article UI could surface explicitly registered pinned proposals at their open-PR heads, but could not automatically discover eligible same-repository review-data PRs. #368 adds automatic bounded discovery, validating four things server-side before returning findings: (1) the PR's immutable head SHA, confirming the tip hasn't moved; (2) the changed-file boundary, confirming the PR touches only expected review-data paths; (3) the registry manifest, confirming the review record is well-formed and registered; (4) the source article blob, confirming it matches the article the review claims to cover. During discovery, head, changed-file, manifest and blob-validation failures are disclosed as unavailable data and prevent new writes. Write-time stale-selection and moved-target checks can separately reject a submission; those responses are distinct from the discovery GET projection. Stale or incomplete history also disables writes explicitly. #368 also adds persistent correspondence, making the review surface a durable pre-merge tool rather than ephemeral browser state. Review registration and article acceptance remain distinct operations.

### Section discussion is durable via GitHub as the correspondence store — *security-as-emergent-ux*

Discussion threaded against article sections was previously ephemeral browser state — it vanished on reload. #368 replaced that with GitHub as the backing store. Saved discussion envelopes carry date, visible article blob, requestId, threadId, actor, and a nullable section label. Reload restores all fields. GitHub was chosen over a separate database or localStorage because it keeps correspondence auditable, co-located with the PR review record, and requires no new infrastructure. On GitHub API unavailability, failed refresh preserves prior receipts as last observed and disables new writes until recovery; proposal discovery failures are reported as unavailable entries with disabled writes. These failure behaviors are covered by controlled ready/outage/recovery tests. Proposal-discovery GET availability and write-time rejection/conflict responses are distinct failure paths. Production rate-limit resilience and broader availability guarantees beyond these tested controls are unknown.
