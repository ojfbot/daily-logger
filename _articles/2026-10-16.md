## The decisions

### Source-pinned review as a first-class editorial gate — *model-behavior-as-design*

"Source-pinned" means the registered review names the article’s source commit and Git blob at inspection time. The review record also carries its full-record hash, and `reviews/registry.json` indexes that record. Test snapshots are a separate seam. These recorded identities let a reader check whether findings apply to particular article bytes after later changes.

PR #362 introduces this registered, source-pinned review pathway as explicitly separate from the acceptance pathway. An editor can read findings and request corrections without the act of opening the UI triggering an acceptance branch. The separation lets an editor request a correction without making an acceptance decision.

The relationship between 'source-pinned' and 'fixture-independent' (commit `4926206`) is this: the pin ties a review to specific article bytes; the fixture independence ties the *test* of that review to those same bytes rather than to the current Git HEAD. The recorded depth-one replay and hosted run reproduced the expected results at PR #362’s publication head `e612f63`, within the boundary of the frozen article inputs. The harness still loads current renderer code, review records, and registry, and the loader deliberately refuses unknown source/date pairs — so the guarantee is bounded to the self-contained article snapshots, not to arbitrary future branches or all CI behaviour.

### Fixture independence from Git history — *tooling-for-iteration*

Commit `4926206` decoupled four specific historical article inputs from live Git history by making them self-contained and hash-checked, removing the `git show` lookup and rendering browser prose and fingerprints from those same frozen bytes instead of current generated API output. The previous loader used `git show` at pinned historical revisions: the failure was that shallow or Git-free checkouts could lack those objects. The browser fixture also read current generated API output instead of the same historical article snapshots. Unrelated commits did not change the bytes at a pinned revision.

The fix records the relevant article bytes directly in the fixture rather than resolving them from Git at runtime. The recorded depth-one replay and hosted run reproduced the expected results for those frozen article inputs. The harness still loads current renderer code, review records, and registry; the loader refuses unknown source/date pairs. This bounded seam is the property that supports CI for review registrations of known articles — it does not extend to a universal guarantee across all checkouts, all branches, or the entire harness. The workflow uses ordinary `actions/checkout` without fetching history, and the source directly reads verified frozen article inputs rather than historical Git at test time.

### Preventing review feedback from triggering provider invocation — *model-behavior-as-design*

Commit `9c8d7ea` addresses accidental provider invocation from review text. The `claude.yml` workflow matches its configured provider mention in newly created comments, submitted PR reviews, and issue bodies or titles on opened or assigned events. A code fence does not neutralise the mention predicate, so review feedback needs encoding before it becomes correspondence.

The fix lives in the comment emitter: when feedback is submitted through the review UI, the emitter escapes every at-sign in display JSON, removes mention-style attribution, encodes artifact paths, preserves exact decoded display and base64 payloads, and performs a final guard rejecting any remaining raw `@` or leading slash before POST. The result is that the provider-trigger workflow sees no matching mention pattern, and the editorial record contains the full correction request with encoded identifiers.

This guard is specific to the checked-in `claude.yml` comment predicate and the `pipeline-alert-commands.yml` leading-slash/label/association guards. Editorial acceptance and revision operate on a separate `accept/<date>` PR path admitted by `pull_request_target` opened/edited events and feedback markers — the comment emitter does not need to make correction and acceptance comments structurally distinguishable because acceptance is not triggered by this comment pathway.

### Post-revision verification as a separate PR — a pilot record — *security-as-emergent-ux*

PR #365 is a standalone verification PR opened after #364 merged. It publishes a Markdown verification record, a structured JSON record, and a registry entry for a focused exact-byte verification at the accepted article head. The service replay performed zero external writes; article bytes, product code, action rows, and original human dispositions are unchanged.

This separate-PR approach is a pilot record of one way to make revision and verification facts independently discoverable. The revision PR (#364) records what changed and why. The verification PR (#365) registers a durable current-review record after the original source review became stale. Independent reviews and fresh checks also preceded #364's merge, providing separate pre-merge evidence. A mandatory second-PR architecture is not established by this pilot and is not required by ADR-0037 or ADR-0038 — it remains an unaccepted design proposal. An independent exact-head check or artifact on the revision PR could in principle also preserve the distinction.

For remaining material findings, retain the failed or pinned evidence, return corrections to the existing editorial authority, and review changed bytes before merge. ADR-0038 documents feedback-edit retries after API failure and its bot-commit loop guard (layer 2). That guard skips revision when the last head commit author contains `[bot]`: after a successful bot-authored revision, editing feedback alone does not rerun the model. A human-directed correction and fresh review are needed; this article does not change that guard. The proposed independent review method says report failure, retain old pinned records, and perform a fresh review when source changes. The October 15 record demonstrates this: the initial revision received two narrow review corrections before final acceptance, then a new current verification record while the original became stale. However, no automatic post-accept verification-failure orchestrator is established — `stampDraft` refuses non-drafts and an existing `accept/<date>` branch. Manual retry under existing editorial authority is available; automatic recovery after acceptance is not qualified. A process clarification documenting this limitation is useful but is not a newly accepted requirement or a gate before the next article cycle.
