## The decisions

### Source-pinned review as a first-class editorial gate — *model-behavior-as-design*

"Source-pinned" means the review is registered against a specific content hash of the article bytes at inspection time — not against a branch tip or a live URL. The pin is recorded in the review fixture alongside the findings, so the fixture can be replayed against the same bytes regardless of what has merged since. This is what makes review results auditable: you can always re-derive whether a given set of findings applied to a given article state.

PR #362 introduces this registered, source-pinned review pathway as explicitly separate from the acceptance pathway. An editor can read findings and request corrections without the act of opening the UI triggering an acceptance branch. The separation matters because conflating 'I want to review this' with 'I want to accept this' is exactly the kind of footgun that shipped wrong articles in the past — the automation layer cannot distinguish intent from action unless the two paths are structurally separate.

The relationship between 'source-pinned' and 'fixture-independent' (commit `4926206`) is this: the pin ties a review to specific article bytes; the fixture independence ties the *test* of that review to those same bytes rather than to the current Git HEAD. Together they mean the review harness produces deterministic results regardless of subsequent commits.

### Fixture independence from Git history — *tooling-for-iteration*

Commit `4926206` decoupled article review fixtures from live Git history. Before this change, a review fixture implicitly depended on the state of the repository at the moment it was run — meaning a test that passed on the day it was written could start failing after unrelated commits landed, producing a class of CI flakiness that is nearly impossible to diagnose because the test output changes without any change to the test or the code under test.

The fix records the relevant article bytes directly in the fixture rather than resolving them from Git at runtime. The fixture is now a self-contained unit: given the same fixture file, the harness produces the same result on any checkout, on any day, against any branch state. This is the property that makes CI trustworthy for future review registrations — without it, a green CI run is evidence of 'passed today' rather than 'passes reliably.'

### Preventing review feedback from triggering comment automation — *model-behavior-as-design*

Commit `9c8d7ea` addresses a specific automation footgun: the acceptance pipeline is driven by comment-based triggers on the PR. The review UI also posts comments — so without a guard, submitting editorial feedback ("correct these eleven errors") and accepting an article ("this is ready to publish") would be indistinguishable at the automation layer, and the acceptance pipeline could fire on a correction request.

The fix lives in the comment emitter: when feedback is submitted through the review UI, the emitter strips or neutralises the specific string patterns that the acceptance automation watches for, while preserving the decoded feedback payload verbatim in the comment body. The result is that the automation layer sees a comment it knows to ignore, and the editorial record contains the full correction request. Someone debugging a mis-fired acceptance PR should look at the comment emitter in the review UI path — that is where the trigger neutralisation happens.

### Post-revision verification as a separate PR, not an inline check — *security-as-emergent-ux*

PR #365 is a standalone verification PR opened after #364 merged. It re-reads the accepted article bytes, independently reproduces the service projection, and confirms zero remaining material findings. It does not modify the article or the acceptance record — it only reads and reports.

The architectural reason this is a PR rather than a step in #364's CI: the acceptance record needs to be legible as two distinct facts. The revision PR (#364) records what changed and why. The verification PR (#365) records that the change was sufficient. If you collapse them — run verification as a required check on the acceptance PR — you lose the ability to distinguish 'accepted after verifying' from 'accepted, verification was a formality.' That distinction matters when auditing an article months later.

The unhappy path is not yet instrumented. If post-revision verification were to find remaining material findings, the current pipeline has no defined re-entry: the cycle would stall at the verification PR with findings unresolved. That gap is acknowledged; the first fully instrumented run is exactly the moment to design the re-entry path before the happy path becomes the only path anyone remembers.
