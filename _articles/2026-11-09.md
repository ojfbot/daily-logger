SQLite fact databases are snapshotted via `VACUUM INTO` from a read-only connection handle — SQLite permits this because `VACUUM INTO` writes only to the new destination path and does not modify the source database or its WAL, making it safe against an active writer. All other data files are written into a content-addressed store on the target mount, keyed by hash; files whose size and mtime are unchanged are skipped. Deleted source files are preserved in older snapshots. `--keep N` (default 4) prunes old snapshot folders while retaining any body still referenced by a kept snapshot's manifest. The `restore-drill` command restores a snapshot to a temporary directory and verifies hash integrity against the manifest — it does not perform a live database swap. This is what 'the drill passes' means: the restored tree's hashes match; the original data is untouched. ## The decisions

### SQLite snapshot via VACUUM INTO on a read-only connection — *security-as-emergent-ux*

DL-6 snapshots fact ledgers using `VACUUM INTO` from a read-only connection handle. This works because `VACUUM INTO` writes only to the new destination path — it does not modify the source database or its WAL journal. Opening the source as read-only prevents any accidental write to the live database and avoids racing an active writer on the WAL. The result is a clean snapshot of the last committed state without touching the live database's journal files.

Tags: `data-layer-integrity`, `hardening`

### Content-addressed store with mtime/size skip heuristic — *tooling-for-iteration*

Backup runs write into a dated snapshot folder on the NAS; files whose size and mtime are unchanged are not re-copied. This makes incremental runs cheap without requiring a full hash pass on every file. The known failure mode: a file silently modified in-place without updating mtime will be missed. This is accepted because the data-root files are either append-only JSONL caches or immutable model weights — neither is edited in-place. That property is currently a design convention enforced by code contract in the write paths, not a filesystem permission. It is an explicit trust boundary: if a crash-recovery path ever rewrites a cache file in-place, this heuristic will silently miss it. That risk is documented and owned.

Tags: `data-layer-integrity`, `content-addressed-storage`

### Append-only target mount: no overwrites, deleted files retained in older snapshots — *security-as-emergent-ux*

No file on the NAS is ever overwritten by a later backup run. A file deleted at the source continues to exist in the snapshot that captured it. Combined with `--keep N` pruning — which drops whole snapshot folders but only after verifying no retained snapshot's manifest still references a body — this gives a simple, auditable recovery surface. Any data loss event can be investigated by walking the snapshot history: everything that ever existed is present until a whole snapshot ages out. This is a recoverable-by-default design: the operator does not need a deduplicating store or a separate versioning layer to answer 'what did this file look like three snapshots ago?'

### Fleet Runner NAS integration splits into independent process observations and owner-controlled claim gates — *assistant-centric*

Six draft PRs opened Sunday across core and BookcaseDiscovery decompose the NAS integration into distinct concerns: authenticated input delivery (core #589, BookcaseDiscovery #90), host-slot sharing and laptop policy (BookcaseDiscovery #91), independent ten-second process observations decoupled from job leases (core #591, BookcaseDiscovery #92), and a draft ADR for NAS tenant identity (core #590). The key design choice: a worker's liveness observation (is this process alive?) is separated from its lease renewal (does it hold an active claim?). A paused, idle, or draining worker remains observable without holding a claim — which is what makes owner-controlled drain and resume coherent. 'Owner-controlled' means the system operator can drain a worker (stop it accepting new claims), pause it (suspend current work), or resume it, without waiting for the worker to voluntarily release. The claim gate enforces this: the server, not the worker, is authoritative over claim state. Note: the ADR in core #590 (`draft-nas-tenant-identity-model.md`) is currently unnumbered and in Proposed status — it is not yet registered in the ADR registry. The authenticated delivery chain in core #589 and BookcaseDiscovery #90 is drafted against the identity model described in that document, but the model has not cleared review. These PRs are speculating forward on an unresolved architecture decision; the ADR must be accepted before they can merge.
