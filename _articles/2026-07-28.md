## The decisions

### OSM multipolygon assembly fixed before the seam validation gate — *model-behavior-as-design*

PR #3 fixed the OSM multipolygon assembly bug as an explicit prerequisite to the co-registration validation, not as a follow-on. The specific failure mode: OSM multipolygon geometries (features like greens and bunkers that are encoded as multiple rings) were not being assembled into coherent polygon objects before projection — which means their bounding extents were wrong and their rendered outlines would have been broken or missing. Running the co-registration correctness gate against those malformed geometries would have produced a false negative: the seam would have appeared misaligned not because the projection logic was wrong, but because the input geometry was broken. The fix had to precede the gate. The principle this encodes is simple but frequently violated: correctness gates must run against correct inputs, or you cannot trust what the gate tells you. This should be the sequencing rule for every future ingestion step added to the pipeline.

### Post-merge status as a first-class PR — *tooling-for-iteration*

PR #4 exists solely to advance ledger state (S2 `delivered` → `merged`) and add an unverified-overlay warning to run instructions. Treating housekeeping as a named PR rather than a direct-to-main push keeps the merge history readable and, critically, keeps the roadmap parser honest. The roadmap parser reads PR titles — a commit message that says 'update status' is invisible to it; a PR title is not. To advance a status correctly: open a PR with a title that matches the parser's expected pattern, do not push directly to main. A direct push will leave the ledger in a stale state that the parser cannot recover from automatically. Note: this is a workflow hygiene call, not an architectural decision — it belongs here for discoverability, but it carries less weight than the multipolygon fix sequencing above.
