## The decisions

### Subpath imports over barrel index in browser-app — *tooling-for-iteration*

The browser app now imports agent-core models via explicit subpaths (e.g. `agent-core/models`) rather than the package root index. The failure mode when using the barrel: even with tree-shaking enabled, Vite's static analysis cannot eliminate side-effect-flagged modules — and some Node-only dependencies in the barrel are marked with side effects, or are imported transitively in ways Vite can't statically trace across package boundaries. The result is a build-time inclusion of Node APIs that don't exist in the browser runtime, causing failures that appear at load time, not at the import statement. Subpath exports are the correct fix because they make the contract explicit at the package boundary: `agent-core/models` resolves only the models sub-tree, and Vite never sees the Node-only paths.

### Inject saved bio/job data into orchestrator requests — *model-behavior-as-design*

The orchestrator was constructing its context object at request time without reading the operator's saved bio and job target from disk, so every run started from scratch regardless of what had been stored. The failure mode in practice: without this data, the tailoring and skills-gap agents receive empty context and produce generic output — a CV that ignores the operator's actual background and the specific job description. The fix injects those records before the orchestrator dispatches to downstream agents. This is a correctness requirement, not an optimisation. **One open question survives Tuesday's patch**: the `/investigate` action at the end of this article asks whether Resume Generator, Tailoring, Skills Gap, and Interview Coach agents consume the injected context from the orchestrator payload, or whether each one constructs its own context independently. If the latter, `ee66a74` fixed the orchestrator-level injection but the downstream agents still start from scratch. This is not yet confirmed either way from the code — answer it before the next feature merges.

### Structured outputs for job analysis agent — *model-behavior-as-design*

The job analysis agent now uses Claude's native structured output feature — specifically, a JSON schema passed in the API call that constrains the model's response to a typed envelope. This is mechanically distinct from a system-prompt format instruction: the API enforces schema conformance before the response is returned, so downstream agents receive a validated object, not a string to parse. The schema is defined in agent-core and shared to the tailoring agent boundary. When the schema changes, a Zod parse at the handoff boundary surfaces the mismatch as a thrown error rather than a silent downstream failure inside the tailoring agent's string-matching logic. This makes the analysis–tailoring handoff deterministic: schema drift becomes a type-system problem, not a runtime mystery.

### Default all agents to claude-opus-5 with 16k max output — *model-behavior-as-design*

All agent-core agents now default to claude-opus-5 with a 16,384-token output ceiling. The 16,384 figure is a practical ceiling (not the model's hard maximum) chosen to bound per-run cost while covering the longest realistic resume generation output observed in testing. The previous default was unspecified — model selection fell through to the API default at call time, producing silent quality variance across runs that was difficult to attribute. Naming the model in the default makes version drift explicit and auditable. **What this decision does not include**: a written rationale for why Opus across all agents rather than a tiered strategy (e.g. Haiku for classification, Opus for generation). A tiered approach was not formally evaluated and rejected — it was not considered at the time. The cost and latency implications of running Opus universally on a pipeline that may run daily or on-demand are real. An ADR capturing the model-selection rationale and the per-run cost estimate at current pipeline depth should be written before the pipeline goes to regular use.

### CLI path resolution from any working directory — *tooling-for-iteration*

The headless generate CLI now resolves all internal paths relative to the script's own location (`import.meta.url` / `__dirname`) rather than `process.cwd()`. `process.cwd()` is a contextual variable — it reflects wherever the operator's shell is at invocation time, not where the script lives. This matters for the CI/CD pipeline and for monorepo operators running the CLI from a workspace root. To run a full end-to-end headless pass from outside the project directory: `node /path/to/cv-builder/cli/generate.js` with no preceding `cd`. The fix is in `2106be8`. A passing run produces a structured output file at the configured output path; a failing run previously produced a file-not-found error on the first internal `fs.readFile` call.

### /pitch-craft and /eli as catalog skills, not ad-hoc prompts — *assistant-centric*

Business communication patterns — Minto Pyramid structuring, MECE decomposition, and dual-register explanation — are now first-class catalog entries in core rather than prompts typed fresh each session. `/pitch-craft` provides an umbrella command plus `/minto` and `/mece` sub-skills. `/eli` produces both an intern-level and an executive-level explanation of a single fact base in one pass. On /eli specifically: this landed on a hardening day because it was ready, not because it was thematically matched to agent debugging. The use case is explaining technical decisions (like those in this article) to mixed audiences without writing two separate documents. Keeping it as a scratch prompt meant the dual-register structure degraded each time it was re-typed. Cataloging it means it's versioned, improvable, and available across all repo sessions.
