## The decisions

### Add _articles/** to deploy-vercel.yml path filters (PR #352) — *security-as-emergent-ux*

The Vercel deploy workflow previously watched only frontend and API source paths, meaning a merged article correction would never trigger a production redeploy — edits would land in Git but silently skip CI and stay undeployed. PR #352 adds `_articles/**` and the workflow file itself to both push and PR path filters. The self-referential watch means PR #352 exercised the new path on its own merge — the fix qualified itself rather than requiring a follow-up dummy commit. The path filter lives in the existing `deploy-vercel.yml` rather than a dedicated article-deploy workflow because article builds go through the same Vercel project and serverless config as the main app; a separate workflow would duplicate environment variable injection and preview URL registration with no compensating isolation benefit. That said, if article and frontend deploy concerns diverge further, a split is the natural next move. Whether daily-logger is publicly accessible right now: the deploy pipeline is live on Vercel, but the canonical public URL is not documented in this article — check the Vercel project dashboard or the `NEXT_PUBLIC_SITE_URL` env var for the current production origin.

### Retire false-premise actions rather than closing them as resolved — *model-behavior-as-design*

Two action IDs were based on incorrect premises about morning-cockpit PR #54 — the article claimed a transition-plan section was missing when an independent review had already confirmed none was absent. Rather than closing these as 'done', PR #350 records them in `api/done-actions.json` as retired false-premise actions, a terminal state distinct from closed-resolved. The practical difference for anything reading `done-actions.json`: a closed-resolved action means the goal was real and was met; a retired false-premise action means the goal itself was not valid — treating them identically would let a downstream consumer conclude the original claim was correct and addressed, which would propagate the bad premise into future queue state. The article doesn't yet document the full terminal-state schema for the action queue (open, closed-resolved, retired-false-premise are at minimum three states); that schema lives in `api/done-actions.json` and deserves its own ADR. How false-premise actions enter the queue in the first place — and what systemic guard prevents recurrence — is not answered by PR #350. That's a gap worth naming honestly: the correction workflow edits the artifact after the fact; the prevention mechanism is not yet defined.

### Inline article corrections with explicit attribution footers — *assistant-centric*

When an accepted article contains a factual error, the correction workflow edits the article source in place, rebuilds the API projection, and attributes the correction with a link to the original accepted Git version and source evidence. The alternative — closing the article as historical and publishing a new one — would break stable article URLs and lose the causal chain between the original claim and its correction. Readers who follow the correction link can inspect exactly what changed and why. This makes the system's correction behavior legible to humans navigating the archive, not just to the agent that generated the next prompt. The tradeoff: in-place edits mean the deployed article diverges from what was originally stamped 'accepted' until the correction PR merges and deploys. The attribution footer is the only signal that a correction occurred; there is currently no diff view or change log surfaced in the article UI itself.
