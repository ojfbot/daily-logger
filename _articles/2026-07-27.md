## The decisions

### f1-doctrine S1 established the compute boundary as a structural constraint, not a convention — *model-behavior-as-design*

f1-doctrine is the retrieval doctrine layer for the Frame OS F1 assistant — it defines what questions the assistant can answer, how those questions are routed to substrate calls, and what persona context governs re-ranking. Without it, routing decisions live in prose in CONTEXT.md, which is unverifiable and unenforced.

S1 committed 33 QuestionNodes — typed records in a registry JSON file, each carrying a `substrate_call` binding field (the name of the substrate function to invoke) and a `phase_key` field (which race phase the question is valid in), but deliberately no result fields. A valid node looks like: `{ "id": "q_gap_to_leader", "phase_key": "racing", "substrate_call": "get_gap_to_leader", "persona": "strategist" }`. An invalid node — one that embeds a computed value like `"result": 3.7` — fails the registry schema immediately at commit time via a CI schema check, not at runtime and not via a prose review. This is the machine-enforceability claim made concrete: the boundary between doctrine (what to ask) and substrate (what to compute) is enforced by the schema validator, not by a human reading CONTEXT.md.

The phase-keying gate is the CI step that validates each node's `phase_key` against a sealed enum of valid race phases. Saturday's gate run showed that hard persona filtering (restricting nodes to a single persona before retrieval scoring) produced a −0.157 delta versus no filter — meaning hard filtering made retrieval *worse* by 0.157 on the scoring metric (a normalized relevance score, 0 = baseline, negative = worse than baseline). That result is what motivated issue #2: make persona a re-rank signal, not a hard exclusion gate. The phase-keying gate passed; the persona filter result is a signal for S2 design, not a failure.

ADR note: the choice to enforce this boundary through schema rather than a runtime check or a linter was made because schema enforcement is the earliest possible catch — it blocks a bad commit rather than a bad deploy. The alternative of leaving result fields nullable (rather than absent) was rejected because nullable fields invite silent population; absent fields make the intent unambiguous. These choices are not yet in a formal ADR file — that's a known gap, acknowledged below.

S2's persona re-rank experiment (issue #2) is designed to score retrieval results across multiple personas — running it with one persona at zero seeds does not produce a 'weak' result, it produces a structurally misleading one, because the absence of seed nodes means the persona has no signal to contribute to re-ranking. ### Issue #4 — 19/33 nodes with zero citation provenance — is a quality concern, not an S2 blocker — *model-behavior-as-design*

This item appears in the open issues list and deserves an explicit disposition rather than silence. 19 of 33 nodes in the S1 registry have no citation provenance — meaning there is no recorded source for why those specific substrate_call bindings were chosen, no link to a race data schema, no reference to an F1 timing feed specification. The downstream risk is reproducibility and auditability: if a node's binding is wrong, there is no trail to determine the correct value from first principles.

This is *not* an S2 blocker in the same way the malformed substrate_call references are. Citation provenance is a data quality concern on a longer timeline; it affects the defensibility of the registry as a production artifact, not the validity of the next gate run.
