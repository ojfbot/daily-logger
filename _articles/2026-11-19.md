## The decisions

### Require both Macs to report fresh readiness before the supervisor admits Bookcase work — *security-as-emergent-ux*

The Bookcase proof involves two machines (Yojimbo and a second Mac) acting as primary and fallback workers. Requiring fresh readiness from both before any work is admitted prevents a scenario where one machine's readiness window has expired and the system proceeds on stale state. Without this gate the proof could start with one worker in an indeterminate state, undermining the takeover verification. The security-as-emergent-ux framing applies here because the gate is experienced as an operator-facing arming flow — the dual-readiness requirement shapes what the human must do before the proof can run, making proof integrity a property of the interaction, not just the code.

Tags: `fleet-runner`, `hardening`, `security-as-emergent-ux`

### Allow proof arming up to ten minutes early inside the approved window — *tooling-for-iteration*

Requiring the operator to coordinate an exact minute across two machines is a usability trap that makes the proof brittle in practice. Allowing arming up to ten minutes before the window's start lets the operator quit and lock both machines at a natural stopping point. The window's hard deadline and integrity checks remain fail-closed, so early arming does not weaken the proof's time-bounding — it only relaxes human coordination overhead.

### Package the FleetRunner proof operator as an installable tarball with CI-enforced proof tests — *tooling-for-iteration*

Keeping the proof logic only in the source tree means a consumer install could diverge from the tested source. Packaging it as a versioned tarball with pnpm pack-verified bins that reject `--invalid` with exit 1 makes the installed artifact the same thing CI tested. The Docker clean-consumer build installs from the tarball into a clean image and re-runs the full 33-test suite plus bin invocations — this is the specific evidence that source-tested and artifact-tested are now the same. Adding `proof:local:test` as a required CI step closes the gap between 'tests pass locally' and 'the installed package works correctly'. To reproduce locally: `pnpm --filter @core/fleet-runner proof:local:test`.

### Isolate the Langfuse exporter behind a child-process boundary — *security-as-emergent-ux*

If the Langfuse SDK serialization blocks, a network request hangs, or the SDK thread deadlocks, a synchronously-coupled adapter would stall the entire article generation pipeline. A child-process boundary means the worst-case failure is a supervisor timeout that kills the child — the main pipeline continues. Operationally, the child is managed by a supervisor with a configured timeout; a hung export surfaces as a timeout-killed child process, not a hung main process. The happy-path trace delivery path is part of the qualification criteria in #571 (qualify inactive Langfuse exporter in delivered fixture images) — that PR is the first point where nominal observability is verified, not just the failure isolation. The boundary is the enforcement mechanism, not configuration flags — this is the same isolation pattern used elsewhere in the fleet for untrusted adapters.
