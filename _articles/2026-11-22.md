## The decisions

### Reproducible two-build CI image as the release artifact — *security-as-emergent-ux*

The FleetRunner release image is built twice from a `git archive` of the same commit in the same CI job; the two image IDs must match or the job fails. This is not a checksum of the image — it is a proof that the build itself is deterministic. Without this, a compromised build environment could produce a different binary from the same source on a second pass, and a single-pass checksum would not detect it; the consumer running `verify-release.sh` would be verifying a property the builder never proved. The double build costs additional CI minutes on every push to main; that cost is judged worthwhile because it converts a trust assumption into a falsifiable check. A consumer running `verify-release.sh` on the downloaded artifact is checking a property the builder already proved, not trusting a single-pass output.

Tags: `fleet-runner`, `ci-cd`, `hardening`

### Test copy is fully isolated — its own Compose project, port, database, and owner identity — *security-as-emergent-ux*

The stage script never touches the production server: `deploy/compose.yaml` gives the test copy a separate Compose project name, port, database, certificate, and `owner` identity with its own keys. The engine never restarts the test copy; it runs only while a staging operation is under way. This boundary is enforced structurally, not by convention — no hostnames, addresses, paths, or keys live in the repo. The alternative — a naming convention that distinguishes test from production — would be a convention any script could violate; the structural separation means a script error cannot accidentally address the wrong instance.

Tags: `fleet-runner`, `ci-cd`, `hardening`

### Stage script rollback on any failure, interrupt, or lost connection — *tooling-for-iteration*

`fleet-stage.sh` follows the same pattern as HelpDesk's stage script: if the copy, load, switch, or smoke-test step fails — or if the terminal connection drops mid-run — the script rolls back to the last revision that passed. This makes staging safe to run from an unreliable connection and means a partial promotion never leaves the test copy in an ambiguous state. The property being preserved is human: a developer should be able to initiate a staging run over a flaky connection without accepting the risk of a half-promoted test environment.

Tags: `fleet-runner`, `ci-cd`

### `pnpm verify` reads workflow files directly — unknown inputs are reported, not skipped — *tooling-for-iteration*

Rather than maintaining a parallel description of what CI does, `pnpm verify` parses `.github/workflows/*.yml` and runs what it finds. Any key, action input, or expression it does not understand is surfaced by name via `--check` — it cannot silently pass a job it doesn't understand. This gives the developer a local CI proxy that degrades loudly rather than falsely. A tool that tells you it doesn't know is worth more than a tool that pretends it does.

Tags: `ci-cd`, `hardening`

### GitHub-only jobs are SKIPPED with a named reason — never silently passed — *security-as-emergent-ux*

`pnpm verify` explicitly names `claude-skill-audit/skill-audit` (posts a PR comment) and `security-scan/security` (reusable workflow from another repo — TruffleHog, key grep, dist guard, pnpm audit) as SKIPPED with their reason. The alternative — silently passing jobs that can't run locally — would give developers a false green and undermine the tool's core premise: a local run should predict what GitHub will do. A false green on a security scan is not a neutral omission; it is a signal that is worse than no signal.

Tags: `ci-cd`, `hardening`

### History replay rather than squash to land the DailyLogger service foundation — *tooling-for-iteration*

#592 replays the 65 non-merge commits of #577 onto current main, preserving authors and messages, with one final commit carrying the content of the five removed merge-commit resolutions. The tree diff against main is byte-identical to #577's reviewed and staged head — verified manually by diffing the replay head against `3e43c07`. Core allows only rebase merges; this approach preserves the full review audit trail — review, staging, and owner approval all carry over — while enabling the rebase-merge that the history shape of #577 prevented. The byte-identical tree diff check was a one-time manual step; there is no automated enforcement on future replays.

Tags: `assistant-centric`, `ci-cd`

### Worker pin-check refuses group/others-writable Node binaries — test harness must match — *security-as-emergent-ux*

The FleetRunner worker's pin check refuses any program with mode `& 0o022` (group or others writable), which is a supply-chain security property: a writable interpreter can be replaced without changing the pinned hash. The deflake fix teaches the test harness to create a private `0500` copy of Node for each test run, matching what a real worker would see on a correctly configured machine. The alternative — loosening the mode check in tests — would have created a gap between what the tests prove and what the production code enforces. A new contributor whose local Node install is `0777` will see the same failure, with an error message that names the mode check; the failure is intentional and the message is the documentation.

Tags: `fleet-runner`, `hardening`
