Native dispatch is ojfbot's mechanism for authorizing Claude to act in unattended contexts: a duty window defines the turn budget, lifetime, tool surface, and built-in profile under which a single qualified model version may execute — without a human in the loop for each turn. The day's architecture is a worked example of how trust is extended incrementally in a system designed to fail closed.

## The decisions

### Exact built-in pin with per-invocation isolation (native-dispatch 0.4.2 → 0.4.3) — *security-as-emergent-ux*

Core pins the exact set of Claude built-in agents and plugins recorded at qualification time, then actively disables all non-security built-ins on each invocation. The alternative — pinning only the binary hash — was rejected because the same 2.1.308 binary reported three plugins in the morning and four in the afternoon of 2026-11-16, proving binary identity is insufficient for behavioral reproducibility. The specific plugin added between the morning and afternoon sessions is not yet identified from committed evidence: the morning qualification trace used format v3 (counts only), not names. The allowlist pin is enforcing against the afternoon profile — the named four-plugin set — and core #615 tracks the unidentified addition as an open issue explicitly outside the correspondence charter's scope. The drift was still worth failing closed on even without knowing which plugin appeared: the system's contract is against a named profile, not a count, and an unacknowledged capability expansion of any kind invalidates that contract.

### Fail-closed on built-in drift, with a registry issue for tracking changes — *security-as-emergent-ux*

When Claude's built-in set changes without a binary change — as observed on 2026-11-16 with 2.1.308 — the allowlist pin refuses any duty turn rather than accepting a modified profile. This creates requalification overhead. How often built-in drift occurs is not yet characterized from committed evidence; the 2026-11-16 observation is the first recorded instance. Requalification is currently a manual process requiring a new qualification session and a PR updating the pinned profile — there is no automated requalification path at this stage. Core #615 tracks the registry of observed built-in additions and removals as a named follow-up explicitly out of the charter's scope.

Tags: `native-dispatch`, `security-as-emergent-ux`

### Preapproved unattended status window as a bounded, distinct approval kind — *assistant-centric*

Rather than extending general correspondence duty to cover status queries, core introduced a separate approval kind for the single-turn unattended status window, with its own digest-checked snapshot contract, 30-minute lifetime, and strict one-turn limit. This keeps the attended and qualification paths unchanged and makes the unattended path auditable by its own distinct trace shape. Mixing the two approval kinds would obscure which authorization chain was responsible for a given invocation — a legibility property that matters as much for incident review as for security.

Tags: `native-dispatch`, `assistant-centric`, `hardening`

### Paired ledger proof: core bounded proof + BookcaseDiscovery installed replay command (CG307-U1) — *tooling-for-iteration*

The FleetRunner ledger proof is delivered as a matched pair — core #618 adds the native supervisor that verifies admission and canonical output, while BookcaseDiscovery #103 adds the installed replay command that validates the full claim lifecycle including real SQLite databases and replay equality. Pairing them under a single charter token (CG307-U1) makes the proof's scope explicit: source review only at this stage, with native admission and setup remaining gated. 'Source-review only, native admission gated' means the code is merged and reviewable but no live invocation runs against the qualified 2.1.308 entry until the gate clears — which requires the owner's explicit sign-off on setup per machine, not just a CI check. Neither side activates without the other's matching evidence.

Tags: `fleet-runner`, `native-dispatch`, `hardening`

### Catalog v2 as a measurement, not a default switch — *model-behavior-as-design*

BookcaseDiscovery's C-11 run re-decided F-0's cached readings against a larger catalog (ISFDB + Open Library) purely to measure how much of v1's no-catalog-match share is a catalog gap rather than a true negative. The default catalog remains v1 and the switch is explicitly the owner's call — the PR committed the measurement without encoding a preference. The 15–20% acceptance recovery figure is meaningful but switching catalogs changes the system's false-positive profile in ways that need deliberate evaluation: a larger catalog accepts more readings, which is only an improvement if the additional matches are accurate rather than spurious. The owner call requires a review of the false-positive delta before adoption.
