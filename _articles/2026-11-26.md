## The decisions

### Rebase-merge strategy immediately surfaces a doctor identity gap — *tooling-for-iteration*

HouseholdAgentKit mandates rebase-only merges (per AGENTS.md), which causes GitHub to rewrite every commit SHA. PR #1's reviewed commit `b9d35d7` became `6220fce` on main, causing `kit doctor` to report the founding review as unverified — a broken state on main. PR #46 is the P1 fix; it is open and not yet merged. No recorded blocker explains the delay: nothing in the supplied context shows it waiting on a stacked dependency or an owner gate, which means the gap is disposition, not sequencing.

The fix in #46 compares tree SHAs rather than commit ancestry. When `kit doctor` runs the review check and fails, the engineer sees the founding review flagged as unverified. The correct inspection tool is `git log --format='%T' HEAD~5..HEAD` (or equivalent) to compare the tree SHA of the original reviewed commit against the tree at each point in HEAD's history. A rebase that lands identical code will produce a matching tree SHA and correctly pass. A rebase onto a moved main changes the tree and correctly reads as unverified — that is not a false positive, it is the intended behavior.

The AGENTS.md rebase-only mandate was not invented for HouseholdAgentKit — it is a fleet-wide convention inherited from core. The tradeoff (SHA rewriting breaks naive commit-identity checks) was not explicitly recorded as a known consequence at the time the mandate was set. PR #46 closes that gap at the kit level.

> **Why does the rebase-merge strategy matter here?** GitHub's "Rebase and merge" button rewrites every commit SHA so that each lands on main as a fresh commit. Any check that verifies "was commit X reviewed?" by walking ancestry will fail on a rebase-merge because the original SHA no longer exists in the graph. The fix — comparing tree SHAs rather than commit SHAs — is the correct level of identity: a rebase that lands identical code should still pass, but a rebase onto a moved main (which changes the tree) should correctly read as unverified.

### FleetRunner promote script redesigned to single-decider model — *security-as-emergent-ux*

Core #751 supersedes #731: where #731 allowed multiple processes to race toward a promote decision, #751 ensures that only one process on the server ever decides — using a journal, bounded steps, and automatic recovery.

The concrete failure scenario that motivates this: FleetRunner's promote path includes automatic rollback on failure. If two processes reach the promote decision concurrently — which is possible under the topology where the promote script can be triggered by multiple callers without a server-side lock — each can independently detect failure and initiate rollback. Two concurrent rollbacks against the same service state produce an ambiguous terminal state: neither process can verify that the other's rollback completed, and the service may land in a partially rolled-back configuration with no clean recovery path. The single-decider constraint eliminates this by ensuring the journal is owned by exactly one process; subsequent callers find the journal and wait or exit rather than racing.
