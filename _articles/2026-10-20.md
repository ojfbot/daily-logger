## The decisions

### Keep evidence bounds explicit and preserve pending outcomes

The observed 903,948-byte packet was a local collection replay, not a retained reconstruction of the original generation input. [#391](https://github.com/ojfbot/daily-logger/pull/391) selects required whole sources before optional sources with stable source-ID ordering, and records what it omits. It does not score discussions by recency or guarantee that every required discussion fits.

The guards remain distinct: 128 KiB per source, 384 KiB across selected source content, and 640 KiB for each serialized request. Source rejection occurs before either action-review call. Each complete request is checked before its corresponding call, so a later verifier-request rejection can follow a proposer call. These byte guards do not establish token-window fit or reserve space for model output. [Issue #386](https://github.com/ojfbot/daily-logger/issues/386) tracks those remaining evidence and context questions.

The three-to-five initial target and two-new-identities revision limit came from the operator's policy clarification, not an empirical derivation from byte capacity. A retry remains part of its existing cycle; it does not replenish an action budget. Revisions must also reconcile work already completed, rejected, deferred or superseded, rather than accumulate another list.

### Bind receipts to the run that produced them

The [#393 repair](https://github.com/ojfbot/daily-logger/pull/393) addressed an observed reader failure: after a workflow pushed a new commit, GitHub's older run response embedded an updated PR head. The immutable run and artifact input/output pins still described the earlier execution. The repaired reader accepted the unedited captured receipt while retaining the PR association, repository, workflow, policy and artifact checks.

A historical input SHA differing from today's PR head is not, by itself, a broken receipt. The evidence supports this reader correction; it does not support declaring all receipts created before the repair weaker or best-effort.

### Make one useful shortlist serve people and coordinating agents

The [#398 card](https://github.com/ojfbot/daily-logger/pull/398) is backed by structured recommendation data and maintenance context used by agents. Readers see a short title, benefit and entry point; an expanded brief carries evidence, scope, expected outcome, owner gates and the next checkpoint. Earlier draft material and handled suggestions remain available without competing with the current shortlist.

The October 20 incident shows why the producer's proposed suggestions must survive independently of admission. Evidence selection stopped before review, and the pending fallback retained draft context while losing the original proposed candidates. Those exact original candidates were not durably captured and cannot now be reconstructed from the surviving notes. Any supervised replacements must be identified as new curation, with their own review evidence. An unverified proposal is neither a queue admission nor authority to execute or close work.

### Supply merge-time evidence in code

[#396](https://github.com/ojfbot/daily-logger/pull/396) derives shipment controls from retained source facts rather than asking a drafting model to invent timestamp metadata. The October 20 artifact contains all eleven genuine merge times. A fresh page load renders their controls, and the #389 control was checked against its October 19 UTC and Chicago values during this review.

The initial article also wrapped full PR URLs inside another PR URL and linked issues #357 and #386 as pull requests. The latter caused a false shipment state for issue #386. Correct source identity and canonical link shape belong in the generation and publication checks: a timestamp coverage check over wrongly typed links can pass while the article is still wrong. The already-loaded older frontend also needed a normal refresh; that observation is distinct from missing evidence.

### Keep historical tests stable while checking current behavior separately

The heading-normalization change broadened extraction code and its tests; it did not rewrite old article history. The later fixture repair froze the authentic older two-option article for compatibility checks and added separate assertions for the maintained three-item card. Six tests had failed because they treated the evolving current article as a fixed historical fixture. The repair removed that mutable assumption rather than weakening the production contract.
