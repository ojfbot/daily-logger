## The decisions

### Whole-discussion evidence selection with bounded new-identity budgets — *model-behavior-as-design*

The action-review pipeline was selecting partial evidence — collector output reached 903,948 bytes against a 393,216-byte source limit because all held suggestion text was included for every record. PR #391 replaced that with whole-discussion selection that prioritizes direct dependencies of the current article's carried or named action identities, records hashes and omission reasons for anything dropped, and enforces a per-revision cap (initial generation: 3–5 identities; each deliberate revision: at most two new identities).

Mechanically, selection walks the set of action identities explicitly named or carried in the current article, scores candidate records by direct dependency to those identities first, then by recency, and admits records greedily until the 393,216-byte ceiling is reached — recording the hash and omission reason for every dropped record. The per-revision identity caps (3–5 initial, ≤2 per revision) are empirically derived from the 640 KiB total ceiling: the initial budget leaves room for system instructions and two agent briefs; the revision cap prevents incremental retries from accumulating identity text faster than omitted records free space.

The 393,216-byte source limit itself is an implementation constant, not a principled design ceiling — its rationale is not documented in the available project context. Issue #386 tracks the deeper fix: a compact global identity index and token-aware admission budget that accounts for system instructions explicitly. Without #386, the current selection holds at the current discussion length but does not provide a hard guarantee against ceiling events as history grows.

Without this fix, every retry accumulated more identity text until the prompt window filled before either review agent could begin.

### Immutable run-input binding for editorial receipts — *tooling-for-iteration*

PR #393 discovered that GitHub mutates the PR head/base objects embedded in an older workflow-run response after the workflow pushes a new commit — the acceptance reader was treating those mutable SHAs as historical execution coordinates and rejecting valid receipts. The fix binds editorial receipts to the immutable run artifact heads rather than the PR object, keeping the exact PR number, API URL, and both repository associations stable.

The failure signature in logs is a receipt status flip to rejected with no generation error — the output is structurally valid but the envelope SHA no longer matches what was recorded at generation time. If you see a receipt failing in this way, the distinguishing diagnostic is: check whether the PR head SHA in the receipt matches the current PR head SHA in the GitHub API response. If they differ and the generation output is otherwise well-formed, this is the GitHub-mutated-envelope failure mode, not a generation fault.

Important provenance note: historical receipts generated before #393 merged used the mutable PR head/base objects as their binding coordinates. Those receipts are not retroactively invalidated by the fix, but they carry a weaker provenance guarantee — the envelope SHA they record may no longer match the GitHub API response for that PR. The chain for receipts generated after #393 is intact. The chain for earlier receipts is best-effort.

The failure mode is subtle: a valid generation output appears rejected not because it's wrong but because GitHub updated the envelope that carried it.

### Single Suggested Actions card as the sole recommendation surface — *assistant-centric*

Articles were accumulating competing priority lists between review attempts — each retry could revive or replace recommendations, and the rendered output showed multiple cards. PR #398 establishes one reviewed top-three card as the canonical surface: full agent briefs, earlier draft notes, and handled suggestions move into closed disclosures, and the same maintenance context reaches both collection and both review agents.

The Suggested Actions card is a rendered human-readable section in the published article — not a data structure consumed by agents. It presents three slash-command action items with descriptions, target repos, and source dates. Earlier drafts and agent briefs are preserved in collapsed disclosure elements in the same rendered output, so the audit trail is accessible without cluttering the primary surface. The design choice matters because parallel recommendation surfaces make it impossible to know which list an independent verifier reviewed — if two cards exist, neither can be the authoritative reviewed output.

### Shipment-time controls derived from immutable source facts — *tooling-for-iteration*

PR #396 found that the October 19 accepted article omitted merge-time controls and ended without useful next-step options despite existing checkpoints. The fix derives shipment controls from immutable source facts and requires a verified closing at publication, carrying the newest accepted handoff into the next cycle with fresh bounded evidence checks.

The alternative — letting the generated closing text stand without source backing — produces articles whose next-step options go stale the moment a PR merges or closes. This is the pipeline-level equivalent of shipping documentation that references a branch that no longer exists.
