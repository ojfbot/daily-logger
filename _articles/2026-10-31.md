## The decisions

### Hold unsupported closure rather than block article acceptance — *model-behavior-as-design*

The failure mode before this decision: if native validation rejected a proposed verified-closure because its citations lacked exact authoritative evidence, the entire acceptance run failed. The article stayed in draft. The alternative considered was to treat any rejected closure as a hard stop — guaranteeing closure quality at the cost of blocking acceptance whenever evidence was incomplete. The decision was to classify that rejection as an evidence-required hold instead. The article reaches Accepted status; the original candidate identities are preserved in Needs Review rather than discarded. The design tradeoff is explicit: closure quality is enforced at the action-review stage, not the acceptance stage, and the pipeline never silently drops candidates. This is the most consequential behavioral decision in the train — it defines what the system does at the boundary between 'verifiable' and 'not yet verified.'

### Expose bounded required GitHub evidence rows as citable lines — *tooling-for-iteration*

PR #508 changed the evidence-view builder to emit original numbered GitHub metadata rows when a complete required discussion fits within the 128 KiB per-source limit. Before this fix, those rows were compressed into a context-only summary that the review model could reference but not cite — meaning a model that appeared to cite specific evidence was actually citing a compressed proxy. The 128 KiB limit is enforced upstream in the evidence assembly step; discussions that exceed it get the context-only view by necessity, and that degradation is now documented as intentional rather than incidental. The lossless view is retained for oversized discussions whose hidden rows are genuinely uncitable.

### Remap closing recommendations through candidate-position tracking during scoped repair — *tooling-for-iteration*

When scoped candidate-association repair removed an invalid captured suggestion, it could shift `closingOptions.candidateIndex` onto a different suggestion. The existing guard refused that index — correctly — but by failing the repair rather than by distinguishing a valid remap from an invalid one. The fix tracks original suggestion positions through the correction pass and remaps closing references to the same retained candidate. The guard still fires if the correction removes the actual target of a closing reference. The invariant is preserved; valid remaps no longer trigger it.

### Reporting workday weekday in article titles is now deterministic — *tooling-for-iteration*

Article dates are anchored to the 03:30 Chicago cutoff, which means an October 29 article covers October 28 work. PR #507 makes the visible weekday name the workday at the start of the reporting interval — Wednesday, not Thursday — computed deterministically at title generation time. An existing leading weekday is corrected or retained without duplication. Historical prose is unchanged; old titles gain the weekday in browser display only. This advances the draft prompt version used for future generation runs.

### Separation of correction, acceptance, and source-pin into distinct PRs is an observed ordering pattern, not an enforced rule — *tooling-for-iteration*

The October 29 train ran as: independent review → correction → evidence repair → hold repair → acceptance → source-pin audit. Each PR had a single stated scope and its own CI gate. The pipeline structurally enforces bounded scope per PR — a CI check rejects PRs that touch more than one workflow stage — but it does not prescribe sequencing order. The observed correction-before-acceptance order worked here and matches the previous article's order, but it is not a mandated invariant. Calling it observed rather than required keeps the decision log credible and prevents the next maintainer from cargo-culting a coincidence into a constraint.
