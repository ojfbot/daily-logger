## The decisions

### Filter macOS power events to the exact scheduled wake before freezing the run window — *security-as-emergent-ux*

FleetRunner 0.2.1 compares only actual macOS wake events when verifying the temporary proof wake, discarding unrelated power events that could otherwise be mistaken for the scheduled one. Without this filter, a lid-open or display-attach event arriving near the scheduled wake time could anchor the run window to the wrong timestamp — the job would start, but its timing evidence would be wrong, and any downstream logic keyed to that timestamp would operate on stale data. Freezing the run start-time only after filtered confirmation — and after the OS has had its full authorization window — means the proof never starts with ambiguous timing evidence. This makes the wake verification auditable: every frozen run start-time is now traceable to exactly one power event.

### Bind the verified wake and its cleanup helper to the later run plan through an idle-worker restart — *security-as-emergent-ux*

The idle worker is intentionally restarted after the proof-wake is confirmed and before the run window opens, so that the cleanup helper is registered against a fresh worker state rather than the pre-proof one. This prevents a scenario where a stale worker reference holds the wrong cleanup handle, leaving the authorized wake unreclaimed on timeout or failure — which in practice would mean the machine stays awake past its intended window with no scheduled return to sleep. The failure mode this prevents is silent resource leak, not loud crash: FleetRunner would appear to run normally while holding an unreclaimed wake authorization. Core #622 is the direct follow-on, addressing the lease handoff boundary that sits immediately adjacent to this restart sequence — if the worker restart itself fails between proof confirmation and run window open, #622 ensures the server lease degrades gracefully rather than being dropped.

### SQLite as the LangGraph checkpoint store for the offline fixture — PostgreSQL deferred — *tooling-for-iteration*

The first daily-logger service fixture uses SQLite for interrupt-and-resume checkpointing across process boundaries. PostgreSQL is an explicitly deferred milestone, not an omission. The sequencing logic: before introducing a network-dependent checkpoint store, the interrupt pattern itself needs to be proven — that a multi-step agent run can pause, persist, and resume in a new process without data loss or state confusion. SQLite makes that proof self-contained and runnable in CI without any external dependencies. What the SQLite fixture unlocks that wasn't possible before: a LangGraph agent run can now survive a process restart mid-flight, recover completed steps without re-executing them, and reject stale inputs that arrive after the checkpoint boundary. That capability exists today in the offline fixture. PostgreSQL is the next milestone (#555, open DRAFT) and is a prerequisite for the blinded comparison phase (#556) before production cutover.
