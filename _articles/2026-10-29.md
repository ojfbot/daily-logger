## The decisions

### Correction gates acceptance: review findings must be addressed before the stamp workflow runs — *model-behavior-as-design*

PR #487 landed before #489 because the editorial pipeline enforces a strict ordering: an independent review must record confirmed errors, a correction PR must address them, and only then can the acceptance stamp be requested. Collapsing these steps — stamping first and correcting later — would leave the public article in a verified-incorrect state with a misleading 'Accepted' label. The cost of the wrong behavior is legible: the stamp's claim of verified accuracy would be false at the moment a reader encounters it. ADR-0038 (editorial revision workflow) defines this ordering as a hard constraint, not a convention. The October 27 train's four-step sequence — #485 → #487 → #488 → #489 — is now the reference cycle for future runs.

### Evidence association is a separate, mechanical prerequisite for the acceptance workflow — *tooling-for-iteration*

PR #488 exists because the acceptance workflow is not purely editorial — it also needs a deterministic evidence map (draftCandidateEvidence) linking each action candidate to its source payload before the proposer-verifier pipeline can evaluate it. The field is a structured object keyed by action candidate identifier; each entry points back to the payload captured at suggestion time. When that field is absent, the workflow has nothing to bind against and cannot proceed. The prior snapshot held three captured suggestions but no draftCandidateEvidence. The repair also resolved a parsing ambiguity: a date-string prefix at the head of a path segment had been misread as a repository name, producing an incorrect binding key. Fixing the key required distinguishing the temporal prefix from the repo identifier — a one-time clarification that is now encoded in the evidence map itself. Separating this mechanical preparation from the prose correction in #487 keeps each PR's diff narrow and independently auditable; a reviewer of #488 can confirm correctness without reading prose changes, and vice versa.

### Source-pinned reviews record a named article blob, not a mutable branch head — *security-as-emergent-ux*

ADR-0038 (editorial revision workflow) and ADR-0037 (editorial stamp workflow) both require the review to pin the exact article source commit rather than a branch name, because branch heads move. PR #485's review record names article source 1fc55540e4dca72c0c5fe20f0f099cf44524eaf8 and blob baae401dd804458021bbf6bf3dc91e43328a8173. Without those pins, a correction commit could silently shift what the review was evaluated against — the review would then attest to a version of the article that no longer exists at the named ref. The failure mode is subtle: the stamp would appear valid, the review would appear complete, and the binding between them would be broken. Commit-hash pinning makes that binding auditable to anyone with repo access, without requiring trust in branch naming conventions. ADR-0037 and ADR-0038 are internal documents; the ruling in brief is that every review artifact must be reproducibly addressable by content hash, not by ref.
