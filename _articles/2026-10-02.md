## The decisions

### Fleet-wide localhost-URL pattern: build-time env guard, not runtime fallback — *security-as-emergent-ux*

Every sub-app that ships a hardcoded localhost URL as its API or remote-entry base fails silently or triggers browser permission prompts in production. The chosen fix — resolving all service URLs through Vite environment variables at build time, with Vercel providing values — prevents any local-dev default from escaping into the production bundle.

A runtime fallback (e.g. 'if window.location is localhost, use localhost') was considered and rejected for two reasons. First, it requires every app to duplicate the detection logic. Second, and more importantly, it would still fail for same-origin Vercel preview deployments. A preview at lean-canvas-abc123.vercel.app is not localhost, so the runtime guard wouldn't suppress it — but it also isn't production, and if VITE_API_URL is unset for that preview, the runtime fallback has no correct value to fall back to. The guard passes, the URL resolves to an empty string or undefined, and the app breaks silently. Build-time enforcement is the only path that makes the failure deterministic and surfaced at build time rather than at visitor load time.

What happens when the env var is unset? Currently, an unset VITE_API_URL at build time produces an undefined interpolation in the Vite config — the remote or API URL resolves to 'undefined' as a string, which fails loudly in DevTools rather than triggering a Local Network Access prompt. That's a better failure mode than localhost, but it is still a failure. The correct guard is: the Vercel project settings for every app in the fleet must have VITE_API_URL (or its app-specific equivalent) set before a production deploy. This is currently operator-enforced, not CI-enforced — see the invariant gap noted below.

The stated invariant — no URL string containing 'localhost' may appear in any build output — is correct but not yet mechanically enforced. There is no CI lint rule, no bundle grep step, and no pre-deploy check. App nine ships with the same bug until someone notices. The honest follow-up action from Thursday's sweep is not the smoke test — it is wiring a `grep -r 'localhost' dist/` check into the Vercel build or a shared GitHub Actions step so the invariant has teeth.

### Eight apps share the same root cause: Module Federation remotes without production URL discipline — *security-as-emergent-ux*

When a Module Federation host resolves a remote entry URL, it uses whatever string is baked into the compiled host manifest — not a runtime config. If that string is localhost:<port>, it is wrong everywhere except the developer's own machine.

The fleet's six simultaneous same-day fixes confirm this was a systemic gap, not an isolated oversight. The pattern was introduced at each app's initial setup: the dev-server URL was used directly in the Vite federation config and never replaced before first deploy. No first-deploy checklist or CI gate caught it because no such check existed. Every app that registered a backend or remote URL without a corresponding Vercel environment variable was vulnerable from day one.

The user-facing cost was real. For purefoy, every visitor who opened the app and typed a chat message received silence — the message hit a dead address at localhost:4001 and was dropped. For gastown-pilot, every page load triggered Chrome's Local Network Access permission prompt — a browser-level interruption for every visitor, every time. For shell, the asset_foundry remote was quietly failing to load for any visitor who wasn't the developer.

The correct invariant is: no URL string containing 'localhost' may appear in any build output. As noted above, this invariant is currently stated policy, not enforced mechanically. A shared lint step in the ojfbot GitHub Actions workflows is the concrete next artifact.

### Fleet-runner supersedes conductor in core — ADR-0108 records the decision, not just the intent — *assistant-centric*

Conductor was the earlier candidate name for the control-plane component responsible for coordinating fleet-runner sessions across the ojfbot app fleet. ADR-0108 rev A records that fleet-runner wins: it lives in core as a dedicated component at a package path inside core rather than a separate repo, and conductor is explicitly superseded.

What does fleet-runner do that conductor didn't? The ADR captures the placement decision; the functional distinction is that fleet-runner is the concrete implementation of the coordination layer — it dispatches session-init signals to sub-apps, manages the shared runtime context, and will eventually gate publication events during pilot phases. Conductor was a naming candidate without an implementation. Fleet-runner is the name that ships with code.

What does resolving ADR-0108 unlock? Core #498 (fleet-runner publication hold docs) can now merge against a stable decision record. The wayfinder map at decisions/wayfinder/control-plane-conductor.md becomes the canonical entry point for anyone who encounters conductor references in older commits. And the correspondence-speech-act-tiers ADR draft (core #495) — which generalizes the coordination protocol fleet-runner will use — now has a settled architectural anchor to reference.

Writing this as an ADR rather than a commit message matters because future sessions will encounter the wayfinder map and need a stable, linkable decision record to reason against. A commit message is searchable but not linkable from other ADRs or issue trackers. ADR-0108 rev A is.
