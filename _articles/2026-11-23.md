## The decisions

### Phase proof requires a close event naming a merged PR, not just a closed issue — *security-as-emergent-ux*

The layer-retro check (`check-trust-phase-proof.mjs`) now verifies that for PR-type slices, the issue's close event must name a merged PR in the same repo as its closer — a hand-close after a linked-but-not-closing PR does not count. This exists because a phase full of closed issues with no actual merged work is indistinguishable from a phase where everything shipped, unless the check reads the close-event source rather than just the closed state.

Mechanically, the script reads GitHub's issue timeline events via the REST API, looking for a `closed` event whose actor is a bot and whose source reference points to a PR in the merged state. The enforcement is asymmetric by design: PR-type slices require a verifiable machine artifact (the merge event); owner-step slices use a completed-status close because their artifact is a physical or configuration action — passkey provisioned, account created — that cannot produce a PR. That asymmetry is the weakest link in the proof chain and is acknowledged: an owner-step slice can be closed without a verifiable external artifact. The check enforces that the close is marked completed-status, but cannot independently verify the underlying action occurred.

This is the *security-as-emergent-ux* framing made concrete: the proof gate isn't just CI hygiene, it's the mechanism that makes the trust build's status legible to anyone who wasn't present during execution. A green retro means something specific and machine-verified, not just 'issues were closed.'

### Deviations sections must have real entries, never the placeholder — *tooling-for-iteration*

Every trust-build slice issue must have its `Deviations and discoveries` section contain either real entries or a plain `None.` line — the filed `_(none yet)_` placeholder (in any spelling, LF or CRLF) is a proof failure. The check matches against the literal string pattern; the exact regex is in `check-trust-phase-proof.mjs`. If a maintainer wants to self-verify before closing a slice, they can run `node scripts/check-trust-phase-proof.mjs --phase PHN` from the core repo root (Node 18+) and read the per-slice output — a dry-run against open slices will report placeholder failures before the retro runs. This design prevents a slice from appearing completed while its learnings are still unrecorded, which would silently break the discoveries chain that feeds the next layer's retro.
