## The decisions

### Pair each suggestion with its own disposition before the verifier runs — *model-behavior-as-design*

PR #440 established that every original suggestion must carry its own proposed disposition into the action-review pair. The prior design allowed a single disputed candidate to block the entire review — one ambiguous entry could silence all others. The verifier still has full authority to approve or reject each pairing independently; the change only prevents one unresolvable entry from holding the rest hostage. This is a pipeline-correctness decision: the queue design was producing an implicit AND gate where an OR gate was intended.

Tags: `editorial-pipeline`, `assistant-centric`

### Run editorial child processes asynchronously so the parent stays responsive — *security-as-emergent-ux*

The sync child-process runner blocked the parent's event loop during long model subprocesses, causing connection closures — specifically, closures on the GitHub webhook channel — to go unprocessed before a receipt POST could fire. The failure manifested as missing receipts with no error: the parent was alive but deaf. PR #440 moved long subprocesses to an async runner so the parent can handle EOF and closure signals in-flight. The 1 MiB raw-output limit, stderr diagnostics, and ordinary error handling are preserved. The pairing fix and the async runner landed in the same PR because the pairing logic triggered the subprocess path; they are separable changes — reverting the async runner does not affect disposition pairing.

Tags: `ci-cd`, `hardening`

### Resolve captured suggestion IDs before the independent verifier reads the proposal — *model-behavior-as-design*

PR #438 fixed a class of review failures where the proposer recopied a captured suggestion with different field values than its canonical record, causing the verifier to see a proposal that didn't match immutable evidence. The fix derives command, repository, and description from the captured record by ID before either reviewer touches the proposal. Invalid references or identity overrides fail early, not mid-review. This is a trust-boundary decision: the canonical capture is the source of truth, and no downstream role gets to silently override it.

Tags: `editorial-pipeline`, `security-as-emergent-ux`

### Admit captured invocations with arguments as ordinary queue entries — *security-as-emergent-ux*

Suggestions like `/owner-gate core#561` carry arguments that previously caused queue admission to fail before the verifier ran, blocking October 21's review entirely. PR #439 admits the exact invocation — with arguments intact — only when it matches an immutable capture and passes native evidence checks. Arguments and admission proof survive save/reload, retries, and later action updates. This grants no execution or owner-decision authority; it only allows the queue to hold the full invocation form that the capture records.

Tags: `editorial-pipeline`, `assistant-centric`

### Repair malformed action output within its originating role, not by restarting the pipeline — *model-behavior-as-design*

PR #441 changed the response to a schema validation failure: instead of restarting the proposer from scratch when the verifier returned a malformed result (or vice versa), the failing role now receives bounded schema feedback — specifically, the validation error message and a diff against the expected schema shape, injected as a constrained correction prompt — and a single retry. The valid, already-validated output from the other role is preserved. The tradeoff is explicit: you spend one retry budget on a shape error rather than the full pipeline budget on a restart. This matters because schema failures at the verifier stage are almost always formatting errors, not semantic disagreements, and a constrained repair prompt reliably fixes them.
