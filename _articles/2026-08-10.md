## The decisions

### D5 generated from the registry, not hand-authored — *tooling-for-iteration*

D5 — the fifth design-handoff document in the `design_handoff_cockpit_v2` program — is produced by reading the registry as a data source rather than written manually. The registry is a structured directory of canonical program state in `core`, consumed by generation scripts (the invocation is a script in `core`'s toolchain, not a one-off command). The failure mode this prevents is concrete: a hand-authored D5 drifts the moment a registry entry changes. In an active program with multiple open PRs, that drift means the handoff document and the actual program state disagree — and code PR reviewers are then litigating design questions that should have been settled upstream. Generating from the registry makes D5's accuracy a property of the toolchain, not of editorial discipline.

### Wayfinder closeouts as evidence gates before code PRs land — *model-behavior-as-design*

The cockpit-v2 wayfinder evidence is committed to `core` before morning-cockpit's Phase 2 code PRs (#44, #45) are reviewed. Wayfinder entries are structured records in the registry that close out a design decision — they assert that a decision was made, when, and by what authority, in a form the toolchain can lint against. The enforcement today is convention-with-lint, not a hard CI gate that blocks PR merge: a linter can verify wayfinder entries exist, but the sequencing — documentation before code — is a team discipline enforced by PR review order. The concrete failure mode this prevents: without a durable evidence chain, code PR review becomes the place where 'was the design sound?' gets re-litigated, which is the wrong forum and the wrong moment.
