### core ([#599](https://github.com/ojfbot/core/pull/599))

PR [#599](https://github.com/ojfbot/core/pull/599) merged at 20:45Z, adding an isolated HelpDesk-to-FleetRunner roundtrip proof. Fleet Runner is the job-dispatch layer that routes signed operator commands to declared-capability workers; HelpDesk is the signed-request gateway that sits in front of it. The proof sends a signed HelpDesk request through FleetRunner, verifies the accepted artifact from original bytes, and returns a signed correlated reply. Sending the same request a second time reuses the existing request, job, and reply without triggering a second execution — proving idempotency at the protocol level, not just in unit tests. The proof uses temporary loopback services, separate synthetic key registries, and fresh state; it closes both services and removes private keys on exit, leaving no residual surface. Independent Claude Code replay on Yojimbo — a separate machine running a separate model session under the same operator — matched all script hashes and seven built-output hash prefixes, confirming the proof is reproducible outside the authoring environment. The independence claim here is same operator, different machine, different session: not a different person, but a different execution context with no shared in-process state.

### core ([#601](https://github.com/ojfbot/core/pull/601))

PR [#601](https://github.com/ojfbot/core/pull/601) merged at 00:24Z Saturday UTC, bundling FleetRunner's versioned declared-command worker. A declared-command worker is one that explicitly registers the kind/capability pairs it is willing to accept before claiming any job; the alternative — a worker that claims jobs speculatively — creates a surface where a worker can receive work outside its declared competence, which breaks the signed-completion audit trail. The worker receives the claimed job and output folder on stdin and uses the existing signed client with fenced output acceptance. The installer verifies an official Node 24 signature before executing, records version/commit/checksum metadata, refuses to install over an existing version without explicit override, and switches the current symlink atomically — meaning the running service either sees the old binary or the new one, never an intermediate state where the symlink points to a partially-written target. The independent review round identified four blocking security defects, all corrected in d51afde before merge: (1) process-group cleanup was not guaranteed when the command root exited before its workers — a valid race under SIGTERM that could leave orphaned children holding file locks outside the signed-completion protocol; (2) HTTP was not restricted to the loopback interface, leaving the worker's HTTP surface reachable by any process on the local subnet without the signed-request protocol; (3) settings and token files were not restricted to no group/other write access, allowing a local user or process to overwrite credential material; (4) repeated TERM/INT signals did not preserve bounded drain in both the worker and the CA parent, meaning a noisy signal storm could bypass the graceful shutdown path. All four were re-verified by the independent review round after d51afde landed.

### Loopback-only HTTP as a security invariant, not a configuration choice — *security-as-emergent-ux*

One of the four defects fixed in d51afde was HTTP not being restricted to the loopback interface. The Fleet Runner worker runs as an installed service; if it bound to a network interface, any process on the local subnet could reach its HTTP surface without passing through the signed-request protocol. Restricting to loopback is a compensating control — a reasonable one — but it raises a design question the article should name honestly: HTTP over loopback requires this restriction as an explicit guard, whereas a Unix domain socket would eliminate the network surface entirely and not require the compensating control. The article documents the fix as shipped; the architectural question of whether HTTP is the right primitive for a local worker is not resolved here and belongs in a future ADR.

Tags: `hardening`, `service-boundary`, `fleet-runner`

### Process-group cleanup must survive the command root exiting — *security-as-emergent-ux*

A second defect from the #601 review: process-group cleanup was not guaranteed when the command root exited before its workers. If the root exits first — a valid race condition under SIGTERM — orphaned child processes can hold file locks or consume resources without the signed-completion protocol ever running. The fix ensures cleanup runs relative to the process group, not the command root's lifecycle. This is the kind of subtle lifetime bug that only surfaces under real OS signal conditions; it is not catchable in unit tests that exercise the happy path.

Tags: `hardening`, `fleet-runner`, `service-boundary`

### Identical-request idempotency as a first-class proof case — *assistant-centric*

The #599 roundtrip proof explicitly includes a duplicate-request case: sending the same request twice must reuse the existing job and reply, not trigger a second execution. In a system where FleetRunner workers claim and execute jobs, a non-idempotent request handler means a replay attack or network retry produces duplicate work, potentially corrupting the job ledger. Proving idempotency at the signed-request level before the worker goes to production is the correct sequencing — the proof exists precisely so this property is verified before it becomes an assumption.
