The headline find of Saturday's session: an adversarial conformance fixture caught a checker silently passing a delivery receipt with no publication intent — because both the receipt field and the expected value were absent, and the checker was comparing `undefined === undefined`. That's a proof that proved nothing, passing cleanly. The fix required schema enforcement, not just a code path patch: `publication_intent` is now a required field in the delivery-receipt type, so the absent-field case cannot reach the equality check. The broader pattern — adversarial fixtures as a first-class contract artifact — caught four more real defects in the same review cycle. Every other commit on Saturday was in service of the same concern: making evidence durable and making its boundaries explicit.

## The decisions

### Adversarial fixtures as a first-class contract artifact, not a CI afterthought — *model-behavior-as-design*

Core #522 seeds 21 conformance fixtures — including adversarial mutations — directly alongside the MC-UX-01 checker, rather than deferring them to a separate test suite. The mechanical reason this worked: two parallel Standards/Spec sub-agent reads would have scanned the checker's logic top-down and found no obvious error. The adversarial fixture approach works differently — it authors a receipt that should fail, runs it through the checker, and observes a pass. That observation exposes the `undefined === undefined` defect in a way that reading the checker cannot. To be precise about the mechanical cause: `publication_intent` was an optional field in the schema, so both the receipt value and the expected value were legitimately absent; the checker's equality test passed because two missing values are equal. The fix is schema enforcement — making the field required — not a code path patch. A second fixture caught an agent-authored settlement passing without an `authorized_by` field by the same mechanism: the field was absent on both sides. Treating 'probe your own logic' as a design deliverable — not a QA step — is what made both defects findable before any real producer or consumer touched the contract.

### Per-body evidence budget with explicit middle-omission markers — *security-as-emergent-ux*

PR #338 caps each merged-PR description at 6,000 characters using a head/tail budget with an explicit middle-omission marker. The marker is the load-bearing element: without it, the model has no signal that a body was shortened and may fill the gap with inference. This article's system prompt explicitly instructs 'do not invent missing conclusions or constraints' from truncated evidence — but that instruction only has purchase if the model can see that truncation occurred. The decision to use a per-body cap rather than a total prompt budget is an explicit partial solution: it prevents any single PR description from dominating the evidence window, but it does not bound the total evidence volume when many PRs are present. Daily-logger #342 tracks that remaining risk. The 6,000-character cap was a reviewer-proposed example adopted in PR #338, with no measured threshold or token-count claim in the review. #342 asks for explicit rationale when choosing the total budget; it does not require an ADR.

### Run provenance captured at generation time, not reconstructed at read time — *assistant-centric*

PR #333 records the responsible authoring stage, model, prompt version, SHA-256, Node version, runner, and job in article frontmatter at the moment of generation — not rehydrated from today's configuration when a reader loads the article. The distinction is consequential: prompt versions and model configurations change. A provenance record derived from current configuration would lie about historical articles — it would attribute a 2026-10 article to whatever model and prompt are running at read time. The record captured at generation time is immutable by design. The authenticated disclosure (expanded for authorized readers) is separate from the static article JSON, which remains public and contains no secret data.

Tags: `assistant-centric`, `ci-cd`, `provenance`

### Unknown publication outcome requires declared reconciliation evidence before correction — *security-as-emergent-ux*

One of the R3 defects in core #522's MC-UX checker was that an unlinked successor could bypass an unknown-publication hold — the checker was not requiring a `corrects` field on approval successors when the publication outcome was unknown. The fix encodes a rule: unknown-outcome corrections must declare reconciliation evidence. This is the same invariant the editorial pipeline uses for article corrections — inline corrections must link the original Git version and attribute the correction explicitly. The pattern is now encoded at two layers: editorial workflow prose convention and the fleet-runner contract checker. The parallelism is not accidental; it reflects a design principle that correction evidence should be explicit and linked at every layer that handles corrections.
