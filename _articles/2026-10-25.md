## The decisions

### Pin historical test fixtures to exact commit SHAs, not live article state — *tooling-for-iteration*

PRs #445 and #446 discovered that the article-completion and missing-receipt-recovery tests both read October 21's live article and action-registry files at test time. Accepting the article caused those tests to fail — not because the production guard was wrong, but because the fixtures were tracking a moving target. The fix extracts fixture inputs into a temporary directory keyed to the exact accepted commit SHA, verifies Git blob hashes before use, and tears down after the suite. A fixture mismatch surfaces as a test error with the expected and actual blob SHAs printed; `git cat-file -p <sha>` is the inspection command. The generalizable principle: tests that assert 'the pipeline rejects a second acceptance' must not depend on live state that changes when acceptance succeeds.

### Introduce Accepted/action-review-pending as a first-class article state — *model-behavior-as-design*

PR #444 recognized that a clean article acceptance and a successful action review are independent operations — the first can succeed while the second hits a recoverable failure boundary. Rather than forcing the whole acceptance to roll back, the new state records the article as Accepted while preserving all original suggestions as Needs review in both the article and the actions index. On subsequent pipeline runs the action-review subprocess is retried automatically against the pending suggestions; no manual trigger is required. Unknown or concurrent-write failures remain fatal; an already-verified Accepted round cannot be downgraded. This state was discovered under pressure, not designed upfront — the October 21 campaign is what proved the two operations needed to be separable. The independence is now explicit in the state machine rather than implicit in retry logic.

### Raise the action-review default context limit to 256k tokens — *model-behavior-as-design*

PR #443 raised the default from 200,000 to 256,000 tokens while keeping the 12,000-token output reserve in place. The change was motivated by measurement: during the October 21 campaign both proposer and verifier were receiving inputs at or near the 200k ceiling, which truncated the evidence corpus available for source-backed suggestion review — the actual failure mode was incomplete review artifacts, not hard API errors. Explicit environment or injected budgets remain authoritative over the default. The 256k ceiling addresses the immediate headroom gap but is not the permanent solution: issue #386 tracks a progressive-retrieval approach that would replace full history ingestion with a compact global identity and a rejection index, expanding only records relevant to the article under review. A local trial of that approach exists at commit 907e490 but is unadopted — the trial established feasibility but integration test coverage for the retrieval path was insufficient to merge. That gap, not a design objection, is what's blocking adoption.

### Register the final October 21 review outcome as a separate PR — *assistant-centric*

PR #447 appended the completed editorial review outcome to the review data files without touching the accepted article source. Separating outcome registration from the acceptance merge preserves the exact tree/blob binding that native schema and correspondence tests depend on — if both operations landed in one commit, the blob hash the tests verify against would include outcome data that wasn't present at acceptance time. Three review-data files changed; all 43 passing tests remained green. The current state: article Accepted, two Sonnet responses recorded, no Opus verification, no action admissions. All three original suggestions remain Needs review and will be picked up by the next authorized action-review run.
