## The decisions

### Selfco capture worker migrates from selfco-box into core as an independent service — *assistant-centric*

The operator's direction (2026-11-13, documented in core #597): the Selfco ingestion worker leaves ojfbot/selfco-inbox and joins core alongside Fleet Runner, with its own deployment lifecycle. For readers encountering Selfco for the first time: Selfco is the daemon that ingests captures from Notion, iOS, and MCP sources into the personal ojfbot/selfco Obsidian vault via a path-jailed Claude agent. It is currently live in selfco-box. The migration follows the same pattern that made Fleet Runner tractable — colocating headless services in a single repo with shared operational infrastructure (env conventions, non-root runtime, immutable image discipline) rather than scattering them across purpose-specific repos where each one reinvents the same deployment machinery from scratch. The economic argument for consolidation is exactly that reinvention cost: every service that lives in its own repo carries its own CI configuration, its own secret management approach, and its own release discipline, none of which transfers. Core #597 is non-draft and eligible for operator review now; no implementation work is authorised until that review closes.

### One untracked env file per application package (core #598) — *security-as-emergent-ux*

Core is becoming a home for deployed headless services — first Fleet Runner, now Selfco workers — and those hosts have no desktop keychain. Core #598 formalises the convention: each application package gets exactly one untracked .env file for local secrets, never committed, and that file is the sole source of environment configuration for the service in local and development contexts. A reviewer will rightly ask: what replaces it in CI and production deployment? That question is not answered by #598 — the PR scopes to local discipline only, and the CI/production secret injection path is a known open item that the convention does not yet close. What #598 does establish is the shape of the gap: by naming the .env file as the sole local source, it makes any deviation from that pattern visible as a violation rather than an ambiguity. This is the kind of discipline that is easy to establish at the second service boundary and painful to retrofit at the tenth. Core #598 is non-draft and eligible for operator review now.

### NAS applications account migration planned before next Fleet Runner gate — *security-as-emergent-ux*

Core #595 records the operator's direction: the NAS fleet apps need a dedicated applications deployment account with application-owned storage, replacing the current dependency on workstation-account home directories. The specific failure the current setup produces: when Fleet Runner or the Selfco worker runs as a job under the NAS, it resolves paths relative to the operator's workstation home directory. That path is valid when the operator is logged in locally, but silently breaks when the NAS is accessed via SSH from another machine, when the operator's home directory hasn't mounted yet at service start, or when any Fleet Runner job runs as a different effective user. Isolating the deployment account eliminates that class of failure by giving the service its own stable home. Core #595 is currently draft; it is not authorised for implementation. Its relationship to core #590 (draft NAS tenant identity ADR) is not yet clarified — whether #590 gates #595 or they are parallel work is an open question that the draft state of both reflects.

### Cross-harness routing gets its first formal authority contract (core #596) — *assistant-centric*

Fleet Runner currently serves BookcaseDiscovery's read-vision queue. Core #596 (draft) plans the routing and authority contracts needed before native Codex and Claude Code sessions can participate in managed workflows. The key insight driving the sequencing: routing semantics need to be formalised at the fleet layer before individual agents start consuming them, or each agent ends up with its own interpretation of what 'authorised' means and the contracts diverge. The concrete failure mode without this: Codex starts consuming the queue with one set of assumptions about what constitutes an authorised handoff, Claude Code starts with another, and Fleet Runner has no way to arbitrate between them. 'Deterministic authority with proof gates' is the design intent — the specific mechanism (what an agent presents, to what system, in what format) is what #596 is being drafted to define. It is explicitly a draft; no implementation is authorised until the routing semantics are accepted.
