## The decisions

### Workers fetch their own inputs — no manual staging before a job runs — *security-as-emergent-ux*

Prior to PR #639, job inputs had to be staged manually before a worker could claim. Workers now download inputs using their own job lease, verify hashes on download and on cache reuse, and present the input folder to the handler in the stdin envelope. The key tradeoff: introducing a network path inside the claim-to-run window adds a new failure class — transport failure, truncation, hash mismatch — but eliminates the entire manual-staging human gate, which is the larger reliability risk at scale. Failure codes (`input-unavailable`, `input-refused`, `handler-pin-mismatch`) are distinct and independently retryable or not, so the service can distinguish transient from structural problems without guessing. What the article cannot confirm from available context: what the operator sees when input fetching fails at scale — whether there is a dead-letter queue, a stale-job accumulation pattern, or an alert surface. The failure-code architecture is defined; the operational response path is not documented here.

### Handler pinning stops a kind from claiming after a mismatch — not just the current job — *security-as-emergent-ux*

When a worker re-hashes its pinned handler files and finds a mismatch, it withdraws that kind from claiming entirely until the worker restarts. This is a deliberate, conservative stance: a changed handler is an operator event that should require a fresh worker launch, not an automatic retry on the next job. If continued claiming were allowed with a mismatched handler, a silently-updated handler could process jobs under the wrong assumptions before anyone noticed. The restart gate makes the mismatch visible and forces a deliberate recovery path. What 'restart' means operationally — whether the worker process exits, whether a fleet command triggers it, or whether an operator must intervene manually — is not specified in the available context. Someone debugging a stuck kind needs that answer; it is an open documentation gap.

### Workers report their own state using only the service's closed vocabulary — *security-as-emergent-ux*

PR #645 gave workers a presence heartbeat, but critically the worker maps every internal reason to a closed set of service-defined eligibility codes before transmitting — `battery`, `power-unknown`, `outside-window`, `resource-busy`, `operator-paused`, and others. Arbitrary internal error text is sanitised to `unexpected-error`. This means the service can reason about worker state without being exposed to internal implementation details, and the operator console can display consistent labels regardless of which worker implementation produced them. Workers report every `presenceMs`; a worker that stops sending heartbeats goes stale after 30 s and is never silently re-eligible, which prevents ghost workers from claiming jobs after a crash. The default value of `presenceMs` and where it is configured are not stated in this window's materials — a sharp edge for anyone operating the fleet, since misconfiguring it above 30 s would cause workers to go stale before their next heartbeat.

### ADR-0110 accepted: work register layer is a first-class module inside FleetRunner, not a sidecar — *assistant-centric*

ADR-0110 formalises that the work register (topics → slices → tasks) lives inside FleetRunner in its own tables with explicit per-table permissions. Roadmap files remain canonical for slice definitions — the register absorbs them field by field rather than replacing them. The audit loop is the sole path that may close an issue; no external tool (GitHub, HelpDesk) owns task state — they hold links only. This prevents the state-authority fragmentation that happens when multiple systems can mark a task done independently. The gap between this acceptance and delivery is currently open: no implementation PR is in-flight.
