# Action intake

`actions/registry.json` is the frozen imported baseline. Bounded `actions/articles/YYYY-MM-DD.json` files hold new identities and article decisions. These files form the canonical action store. `api/actions.json`, `api/done-actions.json`, `api/proposed-actions.json`, and `api/action-dispositions.json` are generated projections. Article prose never admits or closes work. [ADR-0040](../decisions/adr/0040-verified-article-action-registry.md) records the cutover decision.

## Article review cycle

Generation and editorial revision finish with a proposer and independent verifier. Every cycle first reconciles every carried identity: delivered work becomes done, a disproved premise is dismissed, a genuinely replaced obligation is superseded, and waiting work stays open or deferred with its owner and evidence gates. Resolved work leaves the active block and remains in history. Initial generation targets 3–5 useful source-supported follow-ups, admitting at most five new identities. Each later editorial revision or fresh clean-acceptance action review may admit up to two new identities. Fewer or zero new identities is valid; evidence, novelty and independent verification take precedence over the target. The proposer selects source IDs and line ranges. Code resolves their exact text before the verifier judges it; models never have to reproduce quotations. A new identity requires factual evidence, a cited goal, an observable completion condition, and known owner or evidence gates. Revisions retain original descriptions and IDs as history while correcting current actionable wording. The article ends with one maintained Suggested actions card; no authored `What's next` or parallel priority list remains reader-facing.

A continuation choice is presentation, not necessarily queue admission. It may point to a current action identity or to an existing open PR, issue, owner decision, or verified checkpoint without creating a duplicate record. When the same review admits a verified new suggestion, the proposer may point to that candidate by index; application code resolves the index to the single admitted identity before the choice is stored. Queue-neutral checkpoints still pass the same authority and lifecycle boundary: GitHub citations must come from current API or OWNER/MEMBER/COLLABORATOR-authored material, and a checkpoint matching a canonical identity, historical hold, unchanged rejection, protected no-authority record, or owner gate cannot bypass it. Existing canonical work must use its identity and gates. A protected record's immutable invocation scope is canonical even when user-facing prose omits its internal action key; incidental references in descriptions, history, or the explanatory suffix of another invocation do not establish equivalence. A checkpoint must identify its proper entry point, relevant accepted prior-work or review context, why it matters now, the roadmap gap or outcome it advances, and a concrete next checkpoint. Its current disposition is revalidated from primary evidence in the same cycle; yesterday's conclusion cannot become today's instruction by carry-over alone. Closed, merged, completed, dismissed, superseded, stale, or exact-but-irrelevant checkpoints are omitted rather than reissued. A trusted pending human decision may remain visible when it preserves the hold and asks for the decision or verification rather than unauthorized execution. Checkpoint identity uses the canonical target plus distinct outcome; URL fragments cannot manufacture separate work.

The maintained **Suggested actions** card is the single current shortlist. A ready review contains exactly three ranked, distinct recommendations with source evidence, prior-state context, a short familiar-language benefit, a concise start point and a first checkpoint. Canonical outcomes, hashes, protocol language and long safety conditions stay in the disclosed agent brief rather than leaking into the cold-reader summary. The generator's `whatsNext` value is factual reviewer context, not a recommendation surface: the producer encodes it outside visible prose, the review boundary removes legacy top-level `What's next`, `Next actions`, or `Suggested actions` sections, and the dated receipt binds the exact retained value into its state digest. When retained, it appears only inside the card's closed **Earlier draft notes** history disclosure, which states that current follow-ups are ranked above. A missing or changed value invalidates current-format publication; historical accepted and pending-v2 snapshots keep their existing behavior. A newly supported item may displace still-open displayed work without closing its underlying action; the replacement records the prior recommendation identity and explains the evidence-backed rank change. If fewer than three recommendations pass, the supported survivors remain visible with a review-needed prompt, but the new policy cannot publish the article as ready. Resolved suggestions appear afterward in a collapsed **Suggestions handled at draft** disclosure; deferred work remains active rather than moving into handled history. Pending reviews keep the existing generic blocked state and admit no action; preview fixtures cannot substitute for independent verification or accepted continuity.

Every later proposer and verifier receives a compact **recommendation maintenance** projection from the preceding ready or needs-evidence snapshot. It includes each maintained identity and its target or action key, title, and intended outcome, plus every unresolved identity. When a displayed option becomes unresolved, its compact descriptor persists beside the opaque identity through partial review and provider-failure pending state. This projection is explicitly non-authoritative: it carries no historical source bodies or citation quotes and cannot justify display, disposition, replacement, or execution. The current selected evidence and verifier still decide those outcomes; a legacy unresolved identity without a descriptor requires source-bound clarification. The projection is never truncated to fit a prompt—an oversized complete prompt leaves review pending before either agent is called. Pending snapshots preserve the exact prior closing and bind it into state integrity while rendering only the generic blocked state. Their digest covers all decisions for the same article date but excludes later dates, so a legitimate future disposition cannot invalidate a historical pending render or API rebuild while same-day closing and context changes still fail closed.

The next generation receives a bounded accepted-closing continuity projection alongside each prior article's lead excerpt. The projection is bound to the prior article blob, managed article digest, review round and prompt version; it carries whole ranked-shortlist or historical closing presentation fields, evidence identity pointers and the matching independent verdict, but never prior raw source bodies or citation quotes. Fragment-bearing checkpoint links are canonicalized before primary-source slot reservation. Missing, mismatched or oversized projections are explicit unavailable states with whole-option omission counts. Only the newest available accepted closing becomes the active bounded handoff and reserves primary-source collection slots; older projections remain labeled historical background rather than accumulating mandatory retrieval. Any active target omitted by the unchanged collection cap is named as not revalidated and keeps review pending. Current lifecycle, authority and owner gates still decide whether an option may be presented again.

The limit counts newly admitted identities in the trusted logical cycle, including excluded or subsequently resolved identities. Existing active work does not consume a later revision’s two slots. Rewording, existing-identity links, retries and disposal do not create new slots. Trusted callsites provide the phase and stable request identity: generation uses the dated initial cycle; initial clean acceptance uses the PR number plus its intent; PR-body revisions also bind the trusted extractor’s exact feedback digest, so changed human feedback is a distinct request while identical feedback and retries share a budget; continuations use the immutable request comment ID and digest. A recorded pending-generation retry retains its initial cycle. A fresh acceptance review is a follow-up cycle, while a status-only or prose rebind does not create an action-review cycle. Pre-v6 pending snapshots have no recorded phase: acceptance does not infer an initial allowance from their status or history. Legacy suggested identities keep their original data and conservatively consume initial slots. Held historical suggestions remain in compact duplicate context. Each article retains its own rejected candidates for later rounds. Compact global work and evidence fingerprints suppress a rejected candidate on later dates while its cited facts and goals are unchanged. Unrelated source changes do not clear that suppression. New capacity-only holds carry a typed article/cycle scope from the deterministic admission guard. They block the same logical cycle, including retries, but may be reconsidered in a later distinct trusted cycle through a fresh proposer and verifier. No admission or reopening is automatic; semantic rejections and unclassified legacy holds keep their existing behavior. Changed evidence still requires independent verification. An exact held historical suggestion cannot be automatically admitted. Equivalent work requires its existing normalized target and outcome plus independent review. Legacy identities use their immutable command and original description for that match. A shared file or PR number alone does not establish equivalence. Ambiguous equivalence is held.

Draft proposals appear in the Actions page's **Proposed** column. Cleaner and drafting open-work feeds exclude them. A checked suggestion enters the open index only with an accepted review receipt. The checkbox defaults on and saves to the editorial branch. Unchecking retains an article-only suggestion and survives rewording. It cannot close accepted work. Conflicting saves fail visibly and require refreshing the article.

Run an explicit reconciliation:

```bash
ARTICLE_PATH=_articles/2026-10-17.md ACTION_REVIEW_REQUEST=manual:review-2026-10-19 pnpm actions:reconcile
ARTICLE_PATH=_articles/2026-10-17.md ACTION_REVIEW_REQUEST=manual:review-2026-10-19 DRY_RUN=true pnpm actions:reconcile --receipt
```

Reuse the same `ACTION_REVIEW_REQUEST` for retries of that request; a new identity is reserved for a genuinely new human action-review request. The workflow sets it from its trusted PR/comment metadata, never model output. The revision CLI also requires it.

PR-body revision requests require a non-bot GitHub account event even when the current commit has a non-bot author. An edited event must change the extracted feedback; changing unrelated PR prose cannot invoke another revision or create another allowance. A continuation explicitly requested after its predecessor finishes is a new revision, even when the saved notes are unchanged. Duplicate delivery of that same request retains its identity and is not automatically replayed. Account type establishes this request boundary, not independent human authorship or distinct model provenance.

An instructed agent can change an unaccepted suggestion's inclusion:

```bash
ARTICLE_PATH=_articles/2026-10-18.md ACTION_KEY=act-2026-10-18-0123456789abcdef \
INCLUDE_IN_INDEX=false ACTION_ACTOR=ojfbot \
EDITORIAL_FEEDBACK='Keep this suggestion in the article only.' pnpm actions:reconcile
```

`ACTION_ACTOR` must identify the accepting GitHub account. The stored instruction and actor survive later review rounds; acceptance rejects choices attributed to another actor or unrelated registry edits.

The reconciler allows one format repair, with no SDK retries. Each provider call has a two-minute timeout. Linked GitHub discussions are bounded to 12 references. Up to eight goal documents include core’s fleet northstar and roadmap plus linked wayfinder, slice, and convoy documents. Remote evidence shares a 90-second collection budget. Missing sources cannot substantiate a disposition. The 128 KiB per-source, 384 KiB total-source and 640 KiB prompt guards remain unchanged; whole-source selection repairs the observed source-byte rejection; token-window and suggestion-quality qualification remain open under #386. Repository goal files and operator feedback supply goal evidence; the article itself does not prove its claims. Absent goal evidence yields no new admission.

Before either model prompt, selection keeps whole discussions required by carried action records/citations, explicit feedback, or the article’s retained draft continuation context. It keeps complete repository review evidence, local goal documents and the fleet northstar. Other remote goals must be linked by those action dependencies. Historical shipment discussions and unrelated goals remain outside the action review. Selection never takes first/last-N comments: an older owner gate and a later supersession remain together in the full selected discussion. A required missing, partial or oversized source keeps the draft pending before model calls. Optional omitted material is unknown, not proof that an obligation or approval is absent.

An existing action explicitly named by ID in feedback or retained draft context brings its record and cited discussion dependencies into scope even when it originated on another date. Collection prioritizes these direct required references within the existing twelve-discussion limit; more required references than the collector can retain leaves review pending. Sharing a reference with a relevant record can expand duplicate context, but does not recursively require every related record's sources.

Both agents receive every stored action key, exact work key, current state, inclusion preference and protected marker. Relevant records expand with current accepted wording, completion conditions, gates and history; records with existing gates, decisions or protection also expand. Held identities and global rejection fingerprints remain available. Canonical admission checks still use the complete registry, including completed, dismissed, excluded and held work. An unrelated source change does not erase rejection memory.

The dated receipt retains a non-authoritative coverage source listing every collected source’s full-content and collected-content hashes, locator, UTF-8 byte/line counts, inclusion decision and reason. Omitted content is never represented as read. This index cannot support a factual claim, a goal, a terminal disposition or human approval. It describes a bounded collector capture, not an exhaustive repository census. Cached retries retain the exact accepted coverage; source changes invalidate the input fingerprint.

The unchanged ceilings are 128 KiB per included source, 384 KiB total included source content, 640 KiB per complete prompt and 64 KiB per dated action file. The source selector reserves 16 KiB for coverage and still checks its actual size. The provider boundary additionally checks the serialized system/tool/message request against 640 KiB before each SDK call; verifier proposals and repair text also pass the existing prompt check. No source, identity or owner gate is truncated to fit. This is a byte-budget repair for the observed source rejection. Tokenizer counts, model-window fit, output reserves and suggestion quality remain unqualified work under [#386](https://github.com/ojfbot/daily-logger/issues/386); byte fit does not close that issue.

The explicit importer `pnpm actions:migrate` refuses to overwrite a registry. It is not part of generation or API builds. New articles without a receipt and edited articles with stale receipts fail before API output is written. The article and registry are staged in the same workflow commit. Both initial and continued editorial jobs execute the pinned trusted-base policy. The v6 review cache includes the trusted cycle and cannot reuse a v5 receipt. Birth-cycle metadata persists on new identities across current-decision rewrites. Automated admission verifies the output phase and request identity against the trusted workflow and the artifact-bound dated blob. The artifact also binds clean-acceptance versus prose-revision mode and the exact extracted-feedback digest for PR-body revisions, so an actual revision cannot borrow a pending initial retry’s larger allowance. Further acceptance rounds require an exact bot-issued output receipt bound by its hash to an immutable Actions artifact, with matching run provenance and Git ancestry, or an identified inclusion-only change. The existing required Test + pipeline smoke test checks every acceptance PR head without invoking models and waits up to 25 seconds for the post-push receipt. A lost or edited receipt fails closed and requires diagnosis; it never authorizes replay.

Trusted main is the human-reviewed authority, including ordinary source/data PRs and this one-time import. These controls guard automated editorial admission; they are not a cryptographic restriction on a maintainer deliberately approving policy or state changes through a normal PR.

After a terminated local process, confirm that no generation or reconciliation process owns `actions/registry.json.lock` before removing that stale lock. Rerun reconciliation to repair any interrupted article write before publication. CI uses ephemeral checkouts. Ordinary write exceptions restore the prior article and registry; process termination between renames requires this recovery.

## Preserved October 15 contract

- `src/action-intake.ts` recognizes the legacy source forms for the one-shot importer. Normal API builds verify recorded admissions but never extract membership from markdown.
- `action-admissions/2026-10-15.json` is the only admission record in this delivery. It freezes three new IDs, full invocations, exact source lines, dispositions, and authority limits.
- Every admitted source must resolve through the recorded Git commit, path, blob, article SHA-256, line number, and line SHA-256. Required repository evidence carries its own commit and blob identity and is SHA-256 checked before any API file is written.
- `api/actions.json` remains the only open-action feed. `api/done-actions.json` projects accepted completions. Reviewed evidence and dispositions do not settle the protected October 15 records.
- Reviewed actions carry no execution or settlement authority. Drafting and cleaner prompts receive them as continuity context only; they must not recommend, redispatch, or close them.
- The other 138 historical argument-bearing suggestions remain held. Future admission needs another explicit policy decision; recognition alone is not eligibility.

The completed-existing-evidence disposition means its bounded replay has evidence. It does not mean the canonical action is done. A separately accepted exact-ID settlement receipt is required before it can enter `done-actions.json`.

## Tradeoffs

This keeps one product queue and makes the reviewed state visible everywhere that already consumes it. The cost is strict dependence on historical Git objects during API builds, so supported CI checkouts fetch full history and fail honestly when a source commit is unavailable.

Rejected alternatives were a second advisory queue, which left normal consumers blind, and a broad parser backfill, which would have activated 138 unreviewed historical suggestions.

## Verification

Run:

```bash
pnpm check:action-intake
pnpm type-check
pnpm test
pnpm --dir packages/frontend type-check
pnpm --dir packages/frontend build
```

The continuous check compares all 91 imported open and 125 imported completed rows against their pinned Git source. It pins exact historical article appearances and all 138 held source lines, verifies decision citations and source digests, retains three restricted admissions, and builds projections twice to prove byte-stable retry. Lifecycle tests cover draft isolation, cross-day disposal, pre-acceptance corrections, opt-out persistence, stale writes, missing reviews, unsupported completion, and rollback after injected publication failure. Browser tests exercise real checkbox interaction, reload, acceptance branch reuse, and conflicting saves with intercepted GitHub requests.

The browser reads only its dated file. API readers and the deterministic CI check enforce the 64 KiB limit. Repository content from full GitHub links and harvested goal links follows the same public-repository or explicit `REPO_NOTES` opt-in policy as fleet collection. Terminal dispositions require repository evidence, current API state, or a comment from an OWNER, MEMBER, or COLLABORATOR.

A dry run writes no article or queue state, but it still calls GitHub and the configured models unless `MOCK_LLM=true`. Use mock mode for offline checks. See [Action recovery](action-recovery.md) for the pause switch, prose rebinding, artifact expiry, and rollback.
