Continued editorial feedback pilot

The API keeps its existing cookie authentication, ALLOWED_USERS and CSRF checks.
The new feedback-save and explicit revision-request operations additionally require
the authenticated GitHub account and original acceptance-PR author to be ojfbot.
The workflow independently requires the actual owner comment author and original
acceptance-PR author to be ojfbot. A valid explicit owner request on GitHub is
eligible independently of the web allowlist. This shared account proves no distinct
human or agent identity. No Actions copy of ALLOWED_USERS is configured.

Saving a complete superseding feedback version appends correspondence to the same
acceptance PR. The original body and earlier comments are never edited. Saving,
copying, typing and refreshing invoke no model. The separate Request action binds
one saved version to one reviewed PR head and article blob. It authorizes one
attempt through trusted default-branch workflow code. Human merge stays separate.
The original automatic bot-author loop guard remains on the automatic PR events.

Local notes stay editable while saving, awaiting confirmation, stale, or blocked
by an outstanding request. Editing, adding/removing notes and copying a prior
version change only the local draft. An unresolved submitted input retains its
original UUID and exact payload; local edits do not change an eligible exact retry.

An editorial write failure after valid input parsing includes a strict bound
response: error, requestId, intent and outcome. rejected_before_append means this
invocation failed before attempting its GitHub comment append; uncertain means
the append was attempted and its final result is unconfirmed. Encoding finishes
before that boundary. GitHub acknowledgment parsing, author validation and the
complete post-append history load remain uncertain failure phases. HTTP status
alone is insufficient: both 400 and 409 may follow a durable append. Early
authentication, CSRF and parser failures retain generic responses and cannot
release a pending input.

Only a matching explicit rejected_before_append response to the still-live first
invocation can release its pending input so the owner can correct and save again.
A retry can have an earlier uncertain append, so rejection of that retry retains
the same frozen input. Every restored pending input is uncertain; an unreadable
nonempty stored input is preserved and blocks new writes. Malformed, unbound or
mismatched responses also retain uncertainty. A fresh explicit history refresh
can enable an otherwise eligible exact retry or acknowledge a complete historical
record, including one on an older head. Refresh and remount never submit a POST.
A moved head or empty history cannot fence an older in-flight append and cannot
authorize discarding its input or submitting a new UUID.

The consumer compares the pinned PR head against its unique common ancestor with
the trusted default-branch policy commit. Only the dated regular article and canonical registry may differ,
and the article blob must equal the reviewed request. Missing or ambiguous ancestry blocks
execution. Unrelated main commits do not become PR changes; even independent main
changes to the same article do not replace the pinned PR input. This does not merge
main into the acceptance branch or certify mergeability. Workflow code, the revision
script and dependencies still run from the trusted policy checkout, never the PR.

Only one request may be outstanding. A durable pre-provider claim prevents
replay. No-change and changed outcomes are recorded with actual article and registry blob identities.
A claimed failure or uncertain provider/push outcome remains blocked for diagnosis;
this pilot provides no automatic replay or UI override for uncertainty. A workflow
rerun cannot authorize another attempt. Requests must be at most 24 hours old to
execute. Expiry does not clear an outstanding request or authorize a fresh attempt.
Complete execution history must be available.

Operator diagnosis and unresolved pilot limits

If a submitted comment remains uncertain and cannot be reconciled or safely
retried, preserve the frozen input and inspect the acceptance PR's GitHub comments
and relevant Actions runs. Continue editing local notes, but do not reset storage,
open a new tab, or use a different UUID as a recovery procedure. This pilot has no
cancel/fence operation, durable attempt ledger or supported reset for uncertainty.
The submission lock is per tab, not shared across tabs or enforced by a server
compare-and-swap. A fresh tab can submit another UUID; competing feedback versions
with the same parent can make history fail closed and require manual diagnosis.

Manual inspection alone does not unblock the tab. Even if the operator believes a
write never landed, this pilot has no supported reset: new writes remain blocked
until a matching receipt is confirmed or a separately reviewed recovery decision
provides a safe way forward.

For an uncertain or missing receipt, stop further revision attempts. Preserve the
request and feedback digests, comment IDs, input head/blob, claim (including any
lost-response evidence), Actions run IDs/attempts/logs and current remote branch
head. Inspect those records together to determine whether invocation or publication
may have happened. A changed branch alone does not prove which invocation produced
it, and absent comments alone do not prove that a provider was never called.

There is no supported UI or workflow command to unblock an unresolved request in
this pilot. Do not delete correspondence, fabricate a terminal receipt, rerun the
workflow or recreate the branch to force progress. Record the diagnosis on the same
PR and obtain a separately reviewed recovery decision before proceeding outside
this pilot. Closing the PR makes it ineligible; it neither resets execution history
nor proves the invocation outcome, and is not a safe retry procedure.

An undelivered event, cancelled run or dropped pending run can leave a request
outstanding without a claim or receipt. The current default-single concurrency
configuration retains at most one pending run per PR group even with
cancel-in-progress disabled; a later eligible
job can replace a pending one. Legacy automatic PR events share that group with
continued requests. The web path prevents another outstanding request; direct
owner comments can bypass submission checks and make history ambiguous. Consumer
admission rejects unresolved concurrent request history, but is not a durable queue
or recovery mechanism. Inspect Actions runs as
well as PR comments; do not infer that the request was never invoked from silence.

Every issue/PR comment creates an issue_comment workflow event, including unrelated
comments whose jobs skip. The run name still labels automatic PR events as comment
automatic. The history reader scopes to this workflow's issue_comment runs created
at or after the request timestamp and reads at most five pages of 100 runs. Recent
unrelated/skipped events can exhaust that bound. An outage or incomplete history
fails closed before invocation and cannot establish a safe admission-failure receipt;
this is a capacity/diagnostic limit, not evidence that the request never ran. The
local pagination fixtures do not verify GitHub's live server-side filter semantics.

The initial acceptance stamper has its existing branch-existence guard. The editor
also resolves acceptance history before enabling it. Failed or ambiguous discovery
disables acceptance. Main-visible article identity is shown separately from the
pinned PR article reviewed for a continued revision.

Local verification uses pnpm exec vitest run tests/review-surface and the existing
editor/sidebar tests. The consumer fixtures execute the native revision script in
MOCK_LLM mode and push only to a temporary local bare remote. Browser verification
uses pnpm exec playwright test --config playwright.continuation.config.ts after a
production frontend build. These fixtures do not prove deployed GitHub delivery
or authorize any live provider call, workflow execution, production publish or merge.

Action registry cutover

The consumer pins the regular dated article and actions/registry.json blobs at input and output. Registry changes may extend only this article's review history and snapshot; existing identities, earlier evidence, other article snapshots, and other dates' tracking choices stay intact. Missing pre-cutover registry data requires rebasing before any invocation claim. A verified round that changes only the registry is committed and published. No-change means both files are unchanged. Claims and terminal receipts retain both blob identities.

Before the first acceptance, saved checkbox choices can exist on accept/<date> without a PR. Discovery recognizes this branch only after a complete regular-file tree comparison, unchanged draft article, and an inclusion-only registry comparison against current main. Acceptance creates a commit with that exact parent and uses a non-force ref update, so a concurrent branch advance blocks publication.

Subsequent input registry blobs must match canonical ancestor state or an exact immutable bot-issued output receipt from this editorial workflow; an own-article explicit inclusion change is the only human overlay. Receipt checks bind workflow provenance, PR/request identity, trusted policy ancestry, output ancestry, and the regular registry blob. A hand-authored verification snapshot does not establish either agent ran. The required PR check repeats this admission on every acceptance head without model execution, with a short bounded wait for the output receipt. Ordinary human-reviewed source/data PRs retain the normal trusted-main authority.

Owner resolution of a failed clean request

An explicit owner decision may retire a uniquely claimed, completed failure on
attempt1 without starting another run. The original request, immutable claim,
failed attempt and canonical history prefix remain bound in the owner record.
The PR head and article/action-map blobs must still equal the claimed input;
the resolution separately pins the currently observed trusted policy. Complete
workflow history must establish no competing run and the failed run must have
no output artifact. Provider execution, review success and billing remain unknown.

The existing uncertain-receipt evidence and acknowledgment keep their original
serialized shape. When the terminal receipt is absent, the evidence explicitly
records receipt.kind=missing-terminal-receipt and the owner must acknowledge
close_missing_receipt_attempt_without_review_or_billing_claim. This path requires
an explicit complete run-history total as well as bounded pagination. A log line
or ordinary comment saying fetchfailed is not recovery authority. No bot receipt
is fabricated, and a present failed/successful/mismatched receipt cannot use this
missing-receipt path.

The service rechecks evidence before appending the non-executing owner record.
Any later claim, receipt, competing/rerun attempt or artifact holds new execution;
the owner decision and old attempt remain historical. Ordinary noncanonical
correspondence does not change the recovery prefix. The resolved old request is
never executable again. A new hosted request needs separate authority and a new
identity; there is no automatic recovery, replay or retry and no new UI override.
